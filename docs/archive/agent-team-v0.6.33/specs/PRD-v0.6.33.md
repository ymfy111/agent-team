## 0. 本次更新说明

本次更新不是推翻已有原型和产品方向，而是把近期讨论形成的关键架构取舍持续化到正式文档中，避免后续失去对话上下文后只看到零散结论。

核心结论：

```text
当前阶段不要直接建设完整复杂状态机平台。
应先落地“主智能体驱动任务清单 + 系统持久化记录 + 轻量状态约束”的 POC。
后续在任务清单、执行反馈、审查和待决策流程稳定后，再逐步演进到程序状态机编排和多 Runtime 工厂化调度。
```

本产品不是“多个 Agent 自由聊天的群聊工具”，而是围绕项目、任务清单、执行反馈、审查和待决策构建的 AI 软件研发协作系统。


### 1.1 生成层定位

根据最新架构口径，智能软件工厂是 **AI 原生应用平台的生成层 / 建层产品化工作台**。

它的主目标不是管理人力资源，也不是复刻传统项目管理，而是把业务输入、业务本体和语义底座转化为可执行的应用生成流程：

```text
业务输入 / 业务本体
  → Plan / Stage / WorkItem / Task / Step
    → 数字员工 + Skill + Runtime 执行
      → 应用蓝图 / 页面 / 服务 / 配置 / 测试 / 发布包
        → 决策 / 验收 / 反馈 / 持续演进
```

因此，产品页面必须回答“AI 如何生成应用”这个核心问题：当前生成什么、处于哪个计划和阶段、哪个工作项正在推进、哪个任务和步骤正在执行、哪些员工正在参与、哪些规则或决策需要用户介入、哪些产物已经生成并进入验收。

当前总览页、项目页、团队页、员工页、技能页和待决策页都应围绕这条生成链路逐步收敛。

## 1. 产品定位

智能软件工厂是面向 AI 数字员工团队的软件研发协作系统。系统把数字员工组织成团队，以计划、结构化 Markdown 任务单、任务事件、审查记录和待决策事项为协作载体，让负责人能够管理项目进展、观察团队运行、处理关键决策，并逐步将任务执行接入 OpenCode / Claude Code / Codex 等 Agent Runtime。

当前 v0.6.33 原型已经形成以下产品模块：

```text
首页总览 / 协作全景
项目健康总表
团队任务单闭环
待决策工作台
员工 Runtime 绑定页
岗位模板 / 技能匹配页
```

这些模块共同服务于一条产品主线：

```text
用户目标
→ 协同规划岗生成计划
→ 协同规划岗拆解并维护任务清单
→ 系统持久化任务单和任务事件
→ 实现验证岗按任务单执行并反馈
→ 交付审查岗审查结果并触发通过 / 返工 / 待决策
→ 用户只处理关键决策
→ 项目健康总表汇总项目级进度、风险和下一步
```

## 2. 核心角色与职责

### 2.1 协同规划岗

协同规划岗默认是团队组长，是第一阶段的主智能体 / Team Lead。

职责包括：

```text
理解用户目标
生成项目计划
拆解可执行任务清单
维护任务清单变化
接收子智能体执行反馈
判断是否继续执行、进入审查、返工、发起待决策或重规划
向用户汇报关键进展和阻塞
```

### 2.2 实现验证岗

实现验证岗是执行型数字员工。

职责包括：

```text
读取任务单和上下文
执行实现、修改、验证或分析任务
产出执行结果、验证记录、变更说明
将执行反馈回写到任务单或任务事件
```

### 2.3 交付审查岗

交付审查岗是质量门禁角色。

职责包括：

```text
读取任务单、执行结果和产物
判断是否可以交付
形成通过、返工、待决策等审查结论
将审查记录回写到任务单
```

### 2.4 用户

用户不直接处理所有内部任务流转，只在关键节点介入：

```text
需求边界确认
业务取舍
技术方向关键选择
高风险事项确认
验收通过 / 不通过
```

## 3. 第一阶段产品工作方式：主智能体驱动任务清单

第一阶段采用 Agent-led Task List 模式，而不是完整状态机模式。

最小闭环：

```text
1. 用户提出目标。
2. 协同规划岗生成计划。
3. 协同规划岗拆解任务清单。
4. 系统保存计划和任务单。
5. 程序按任务单指派对应数字员工执行。
6. 实现验证岗执行并反馈结果。
7. 系统记录任务事件。
8. 协同规划岗读取任务清单和反馈，更新下一步。
9. 交付审查岗进行审查。
10. 必要时进入待决策工作台。
```

在这一阶段，主智能体仍然负责大量计划、判断和维护任务清单的工作；系统主要负责持久化、展示、轻量约束和调用记录。

## 4. 结构化 Markdown 任务文档需求

项目过程中的计划、任务、审查和待决策文档继续使用 Markdown，但必须逐步从“纯自由文本 Markdown”升级为“带结构的 Markdown”。

目标：

```text
人和智能体阅读 Markdown 正文。
程序读取和更新 YAML Front Matter 中的结构化字段。
程序或智能体只更新被标记的局部区块，避免重写整篇文档。
```

### 4.1 任务单 Markdown 的最小结构

```md
---
id: TASK-001
title: 用户管理页面迁移
status: TODO
ownerRole: implementer
ownerAgentId: emp-impl-1-1
priority: P1
nextStep: 执行页面组件迁移
decisionRequired: false
updatedAt: 2026-05-21T10:30:00+08:00
---

# 任务说明

这里写给人和智能体看的背景、目标、约束和执行要求。

## 执行反馈

<!-- agent-feedback:start -->
等待执行反馈。
<!-- agent-feedback:end -->

## 审查记录

<!-- review:start -->
等待交付审查。
<!-- review:end -->
```

### 4.2 程序读写边界

```text
程序优先读取 Front Matter 字段，例如 status、ownerAgentId、priority、nextStep。
程序只更新可控字段和带标记的区块。
人和智能体可以阅读和维护正文上下文。
任务历史事件建议追加到 JSONL Event Log，避免整篇 Markdown 被频繁重写。
```

| 原型模块 | 当前契合度 | 新口径中的定位 |

| 首页协作全景 | 高 | 团队运行态和任务单状态聚合视图 |

## 6. 当前不做的产品范围

为避免过度设计，v0.6.33 后续实现阶段暂不做：

```text
完整复杂状态机引擎
多级任务依赖图
全自动多 Runtime 调度
复杂失败重试策略
全链路审计平台
Agent 自由群聊式协作
```

这些能力作为后续阶段演进方向，而不是第一阶段 POC 的前置条件。

## 7. 验收口径

后续原型和实现应能回答：

```text
组长如何生成计划？
任务清单在哪里？
任务分派给谁？
子智能体执行后如何反馈？
任务状态如何变化？
审查结论如何回写？
用户何时介入待决策？
项目健康如何由任务清单汇总得到？
```

只要这些问题在原型、文档和后续 POC 中能被清楚回答，即可认为当前阶段产品口径成立。
---

## 8. 结构化 Markdown 协作要求

当前阶段的计划、任务、审查和待决策仍以 Markdown 为主要协作格式，但必须带结构，便于程序读取和更新关键字段。

产品要求：

```text
1. 协同规划岗生成的计划应保存为结构化 Plan Markdown。
2. 每个可执行任务应保存为结构化 Task Markdown。
3. 子智能体执行反馈应回写任务单的标记区块，并形成任务事件。
4. 交付审查岗审查结论应形成结构化 Review Markdown。
5. 需要用户判断的问题应形成结构化 Decision Markdown，并进入待决策工作台。
6. 程序只更新它关心的结构化字段和标记区块，不应覆盖正文上下文。
```

这样既保留 Markdown 对人和智能体友好的优势，也为后续轻量状态约束和程序状态机演进预留接口。

## 9. 用户界面稳定与底层机制演进原则

本轮新增产品原则：**界面稳定，机制演进**。智能软件工厂的用户界面不直接暴露“状态机、TaskEvent、结构化 Markdown、Runtime 编排”等底层实现细节，而是稳定围绕以下用户可见对象展开：

- 项目是否在推进；
- 团队当前在执行什么；
- 协同规划岗、实现验证岗、交付审查岗分别产出了什么；
- 哪些任务进入审查、返工或待决策；
- 用户需要做什么业务取舍。

底层可从“主智能体维护结构化任务清单”逐步演进到“程序状态约束 / 状态机编排 / Runtime 工厂化调度”，但普通用户心智保持不变。

### 9.1 岗位产出表达

原型与后续产品界面应优先展示岗位实际产出：

| 岗位 | 用户可见产出 | 不作为主界面重点暴露 |
|---|---|---|
| 协同规划岗 | 计划草案、任务拆解、风险说明、下一步动作 | 状态机节点、内部 TaskEvent |
| 实现验证岗 | 代码变更、配置变更、验证记录、问题反馈 | 底层执行日志细节 |
| 交付审查岗 | 审查结论、返工意见、验收建议 | 审查引擎内部规则 |

### 9.2 Mock 数据真实性要求

Mock 数据不应只展示抽象机制名，而应贴近真实项目推进过程，包含项目阶段、岗位产出、任务进度、待审查、待决策、下一步动作和风险说明。
