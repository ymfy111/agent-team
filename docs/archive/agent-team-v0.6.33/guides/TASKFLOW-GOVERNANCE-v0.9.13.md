# TASKFLOW-GOVERNANCE v0.9.13

> 文档类型：任务流执行治理指南  
> 适用对象：新会话、新智能体、taskflow skill 维护者  
> 对应 skill：`skills/taskflow/SKILL.md` v0.9.13

## 1. 固定启动节点清单格式

后续任务流启动或恢复执行前，默认使用以下格式，不再因会话变化随意改变。

```text
任务流：TF-XXX｜任务流名称
基线：...
验收模式：委托验收 / 人工验收 / 混合验收
冻结项：...

| 节点 | 名称 | 目标 | 验收点 | 预计耗时 |
|---|---|---|---|---|
| TF-XXX-N01 | 节点名称 | 本节点要达成什么结果 | 怎样判断节点完成 | 低复杂度 / 中复杂度 / 高复杂度，或宽区间 |
| TF-XXX-N02 | 节点名称 | ... | ... | ... |

总预计耗时：粗粒度区间或复杂度等级。
请确认是否按以上清单执行。
```


## 2. 执行后节点进度表格式

任务流启动清单格式保持第 1 节不变；节点执行后、节点完成后和最终总结中的**节点进度日志**统一使用以下 7 列：

```text
| 节点 | 目标 | 结果 | 验证 | 证据 | 预计耗时 | 实际耗时 |
|---|---|---|---|---|---|---|
| TF-XXX-N01 | 本节点目标 | 完成结果 | PASS/FAIL/评审结论 | 文件/截图/命令/报告 | 预计区间 | 实际或未精确计时 |
```

说明：

1. `节点` 使用 nodeId，不再把节点名称作为必填列；必要时可在结果中补充名称。
2. `目标` 来自节点清单的目标，便于对照计划。
3. `结果` 写实际完成内容，不写空泛“已完成”。
4. `验证` 可合并 QA 结果与独立评审结论。
5. `证据` 必须指向截图、文件、命令输出、报告或写“无”。
6. `预计耗时` 使用粗粒度区间或复杂度。
7. `实际耗时` 只有可信计时时才写具体值，否则写“未精确计时”。

## 3. 进度缓存与主对话推送

长程任务不能只在工具活动或缓存里推进。taskflow 必须使用脚本缓存记录节点生命周期，并把缓存进度同步到主对话窗口。

```text
缓存事实源：.runtime/exec/taskflows/<taskflowId>.json
开始节点：taskflow.mjs start → 写入 start event
完成节点：taskflow.mjs done/fail → 写入 done/fail event
生成待展示文本：taskflow.mjs render-pending
用户可见后标记：taskflow.mjs mark-rendered
最终兜底：taskflow.mjs visible-summary / summary
```

同步节奏：

```text
- 默认：每个节点开始和完成后都要同步 pending 事件到主对话；
- 若做不到节点级同步：至少每完成一个可见子阶段、每 2-3 个工具批次，或长时间执行时约每 10-15 分钟推送一次缓存进度；
- 定时推送必须来自脚本缓存，不能只靠模型回忆；
- 最终回复必须包含完整 7 列节点进度表。
```

## 4. 为什么要固定格式

1. 用户可以快速比较不同任务流的范围、目标和验收点。
2. 新会话接手时更容易恢复上下文。
3. 节点清单能直接映射到未来产品里的 WorkPackage / TaskTicket。
4. 避免模型每次根据表达习惯重排格式，造成阅读和执行成本。

## 5. Skill 更新同步规则

修改 `skills/*/SKILL.md` 时，必须同步检查：

```text
skills/<skill>/README.md
skills-README.md
docs/文档导航.md
docs/guides/* 或 docs/reports/*
交接说明或版本说明（如本轮涉及）
```

如果 `SKILL.md` 内容较新，但 README / 导航 / 版本说明没有同步，应判断为“配套文档同步缺口”，不能反向推断 skill 不是最新。

## 6. 与产品化的边界

本治理规则面向当前执行技能，不等同于最终产品 UI。产品化时应将内部术语转译为用户可理解概念：

| skill 概念 | 产品化表达 |
|---|---|
| taskflow | 项目推进计划 / 工作包流 |
| node | 可验收工作包 / 阶段任务 |
| pause gate | 待决策 / 阻塞 / 风险门禁 |
| evidence | 验证证据 / 交付产物 |
| visible-summary | 阶段汇总 / 进展报告 |

## 7. 验收标准

后续 taskflow 输出合格的最低标准：

1. 启动清单使用固定表格；
2. 节点目标和验收点不为空；
3. 节点完成后最终回复包含完整 7 列节点进度日志；
4. 涉及前端/UI 的节点提供截图或说明无法截图原因；
5. 无法精确计时时明确写“未精确计时”；
6. 节点进度必须来自脚本缓存，并按节点完成或定时推送到主对话；
7. 修改 skill 时同步配套文档。


## TF-GOV-04 补充：生命周期事件与实际耗时口径

v0.9.13 针对模拟测试暴露的问题补充以下硬规则：

1. 每个节点必须分别同步 `▶️ 已开始` 与 `✅ 已完成` 事件到主对话窗口。
2. 完成事件必须显示 `进度 <done>/<total>`，其中 done 是已完成节点数，不是节点序号。
3. 只要脚本缓存中存在可信的 `startedAt` 与 `completedAt`，必须计算并输出 wall-clock 实际耗时；模拟任务也不例外。
4. 只有缺少开始/完成时间、跨回合暂停、等待用户、或 start/done 未覆盖真实执行过程时，才允许输出“未精确计时”。
5. 回归测试必须覆盖至少两个后续节点，不能只验证 N01。
