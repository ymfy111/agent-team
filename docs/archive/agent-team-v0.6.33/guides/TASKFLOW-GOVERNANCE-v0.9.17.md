# TASKFLOW-GOVERNANCE v0.9.17

> 文档类型：任务流执行治理指南  
> 适用对象：新会话、新智能体、taskflow skill 维护者、上层 taskflow runner / 调度器  
> 对应 skill：`skills/taskflow/SKILL.md` v0.9.17

## 1. 固定启动节点清单格式

任务流启动或恢复执行前，默认使用以下格式，不再因会话变化随意改变。

```text
任务流：TF-XXX｜任务流名称
基线：...
验收模式：委托验收 / 人工验收 / 混合验收
冻结项：...

| 节点 | 名称 | 目标 | 验收点 | 预计耗时 |
|---|---|---|---|---|
| TF-XXX-N01 | 节点名称 | 本节点要达成什么结果 | 怎样判断节点完成 | 低复杂度 / 中复杂度 / 高复杂度，或宽区间 |
| TF-XXX-N02 | 节点名称 | ... | ... | ... |

总预计耗时：粗粒度区间或复杂度等级。
请确认是否按以上清单执行。
```

## 2. 默认执行模式：低打扰自动推进

v0.9.17 将“检查点模式”降级为测试/降级/人工验收专用。真实长程任务默认采用 **auto-visible mode**：

```text
用户确认任务流 → 节点自动推进 → 每个节点 start/done 输出到主对话正文 → 仅触发门禁才暂停 → 最终总结
```

执行要求：

1. 用户确认任务流后，节点之间自动继续，不要求用户逐节点回复“继续”。
2. 每个节点开始时，主对话正文必须出现 `▶️ <nodeId> 已开始`。
3. 每个节点完成时，主对话正文必须出现 `✅ <nodeId> 已完成，进度 <done>/<total>`。
4. 普通节点通过后自动进入下一节点。
5. 全部完成后输出完整 7 列节点进度表。

## 3. 暂停门禁

只有以下情况才暂停请求用户介入：

```text
- P0/P1 风险或可能破坏当前基线；
- 范围变更或冻结项需要调整；
- 关键产品/技术决策；
- 依赖缺失且执行者无法自行补齐；
- 验证/评审多轮修复后仍不收敛；
- 需要用户验收、同步、下载、发布或授权；
- 用户明确要求逐节点人工验收。
```

普通节点完成、普通验证通过、普通文档/脚本修改通过，不应要求用户点“继续”。

## 4. 节点进度表格式

任务流启动清单格式保持第 1 节不变；节点执行后、阶段总结和最终总结中的**节点进度日志**统一使用以下 7 列：

```text
| 节点 | 目标 | 结果 | 验证 | 证据 | 预计耗时 | 实际耗时 |
|---|---|---|---|---|---|---|
| TF-XXX-N01 | 本节点目标 | 完成结果 | PASS/FAIL/评审结论 | 文件/截图/命令/报告 | 预计区间 | 实际或未精确计时 |
```

普通节点中途不默认插入 7 列表格。7 列表格默认用于阶段总结或最终总结。

## 5. 中途进度推送规则

中途推送要“少而有用”：

```text
普通节点：只输出 start/done 简洁过程；
长节点：超过约 10-15 分钟无可见输出，或节点复杂/风险较高时，推送一次阶段性进度表；
用户询问：用户问当前进度时，立即基于脚本缓存输出 7 列进度表；
风险/阻塞：出现风险、阻塞、验证失败或修复循环时，立即输出当前状态和下一步处理。
```

不要在每个普通节点中途无意义插入完整进度表，避免干扰阅读。

## 6. 进度缓存与主对话推送

缓存事实源仍是：

```text
.runtime/exec/taskflows/<taskflowId>.json
```

最小链路：

```text
start → 写入 start event → render-pending → 主对话正文发送 start → mark-rendered --confirmed-main-chat
done/fail → 写入 done/fail event → render-pending → 主对话正文发送 done/fail → mark-rendered --confirmed-main-chat
最终 → validate-visible → summary / visible-summary
```

注意：`mark-rendered --confirmed-main-chat` 只能在 pending 文本已经真实出现在主对话正文后使用。Activity、工具日志、脚本输出和最终代码块回放都不算主对话正文可见。

## 7. 运行环境要求

- 若运行环境/上层调度器支持多次普通助手消息推送，必须采用 auto-visible mode。
- 若当前 ChatGPT 单轮无法真实推送中间普通助手消息，可以在测试或降级时使用 checkpoint mode。
- checkpoint mode 不能作为长程任务默认方案，不能让用户为了无风险普通节点反复点“继续”。
- 若既要求无人值守，又要求过程消息实时进入对话框，需要由上层 taskflow runner / 调度器承担消息推送能力。

## 8. 检查点模式的边界

检查点模式只适用于：

```text
- 测试 skill 输出格式；
- 当前环境确实不能自动推送主对话过程消息；
- 用户明确要求逐节点人工验收；
- 高风险任务需要每个节点确认。
```

检查点模式下一个节点一回合，但这不是默认执行体验。

## 9. Skill 更新同步规则

修改 `skills/*/SKILL.md` 时，必须同步检查：

```text
skills/<skill>/README.md
skills-README.md
docs/文档导航.md
docs/guides/* 或 docs/reports/*
交接说明或版本说明（如本轮涉及）
```

如果 `SKILL.md` 内容较新，但 README / 导航 / 版本说明没有同步，应判断为“配套文档同步缺口”，不能反向推断 skill 不是最新。

## 10. 验收标准

后续 taskflow 输出合格的最低标准：

1. 启动清单使用固定表格；
2. 用户确认后默认自动推进，非必要不暂停；
3. 每个节点 start/done 真实进入主对话正文；
4. 完成消息包含进度 x/y、验证、证据、预计耗时、实际耗时；
5. 普通节点不无意义插入中途 7 列表格；
6. 最终总结包含完整 7 列节点进度日志；
7. `validate-visible` 通过；
8. 修改 skill 时同步配套文档。

## v0.9.17 实战修正：不要把不可见过程当成可见过程

本轮真实任务截图显示，单轮 ChatGPT 回复中间过程可能只渲染一部分：用户能看到 N01 start/done 和 N02 start，但 N02 done、N03、N04 只在最终总结或隐藏过程里出现。这种情况必须判定为过程可见性不合格。

治理规则：

1. 主对话正文可见是唯一用户可见口径。Activity、工具日志、commentary、折叠代码块、最终回放不能替代真实过程输出。
2. `auto-visible mode` 需要运行环境/上层 runner 能连续推送普通助手消息；若没有该能力，不能宣称“无人值守且实时过程完整可见”。
3. 普通 ChatGPT 会话应在两种模式中诚实选择：
   - `checkpoint-visible`：可见性优先，一个检查点一回合；
   - `batch-auto-summary`：无人值守优先，完成后输出完整审计总结，但不声称实时逐节点可见。
4. 实际耗时必须由可信 start/done 账本计算；若截图显示 startedAt/completedAt 与 actual 不一致，该节点验证 FAIL。
5. 真实软件工厂产品应由平台事件流（例如 SSE/WebSocket/任务事件总线）承担进度推送，不应依赖一次 LLM 回复完成实时 UI。
