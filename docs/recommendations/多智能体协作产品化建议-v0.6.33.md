# 多智能体协作产品化建议（v0.6.33）

> 目的：把当前“多个智能体 + 用户 + Git 仓库”协作推进 `agent-team` 项目的真实过程，抽象为智能软件工厂的核心产品能力参考。  
> 适用对象：后续设计侧智能体、实施侧智能体、项目负责人。  
> 版本口径：v0.6.33 / 原型 v0.6.33.45 / TF-P0B-05 后。

---

## 1. 核心判断

当前 `agent-team` 的研发方式，本身就是智能软件工厂的第一批真实业务样本。

```text
当前真实协作：
  设计侧智能体产出 PRD / SDD / 任务流 / 原型 / 交接文档
  实施侧智能体落盘代码 / 跑 QA / 提交 git / 更新项目记忆
  用户负责触发同步、验收和关键决策
  Git 仓库承载最终事实

产品化目标：
  软件工厂把以上人工协调动作系统化、可追踪、可验证、可恢复。
```

因此，建议把“当前人工多智能体协作链路”明确纳入产品设计，不只作为临时开发流程。

---

## 2. 当前实践到产品能力的映射

| 当前实践 | 产品化能力 |
|---|---|
| 设计侧智能体输出 PRD、SDD、原型、任务流 | 协同规划岗：需求沉淀、方案设计、任务拆解 |
| 实施侧智能体编码、测试、提交 | 实现验证岗：任务执行、验证、回执 |
| 用户验收、决策仲裁 | 待决策机制 + 交付审查岗 |
| Git 仓库作为最终事实源 | ProjectRepository / Artifact Store |
| docs/ 与 apps/ 作为交接契约 | TaskTicket / WorkOrder / Artifact / Evidence |
| handoff/update 文档说明当前状态 | HandoffPackage / BaselineSnapshot |
| 实施前先 pull、读文档、跑 QA | BaselineCheckTask |
| 发现设计缺口后反馈，不擅自改设计 | ChangeRequest / DecisionItem |

---

## 3. 建议补充的核心产品对象

### 3.1 WorkerWorkspace：外部工作空间

不同智能体可能运行在不同环境中：本地持久工作区、云端沙箱、浏览器会话、远程容器等。产品需要显式建模工作空间，而不是假设所有 Worker 都在同一运行环境。

建议字段：

```text
WorkerWorkspace
- workspaceId
- workerId
- projectId
- sourceType: local / sandbox / remote / browser-only
- syncMethod: git / patch / zip / manual
- persistence: persistent / ephemeral
- readableScopes: docs / apps / prototypes / reports
- writableScopes: docs / apps / reports / none
- lastSyncedCommit
```

价值：

1. 解释“为什么有的智能体能直接改代码，有的只能产出文档包”。
2. 让系统知道某个产出是否已进入事实源。
3. 为后续多 Runtime 调度、权限隔离和恢复提供基础。

### 3.2 ProjectRepository：项目事实源

当前协作里，聊天内容不是事实源，Git 仓库才是事实源。

建议原则：

```text
ProjectRepository = 项目事实源
Conversation = 过程上下文
Sandbox File = 临时产物
Committed Artifact = 有效产物
```

产品上需要把“是否已落盘到仓库 / 是否对应 commit / 是否通过 QA”作为任务状态的一部分。

### 3.3 HandoffPackage：交接包

`update/HANDOFF-*.md` 这类文档应被抽象为一等对象，而不是自由文本附件。

建议结构：

```text
HandoffPackage
- packageId
- projectId
- baselineVersion
- taskflowId
- sourceCommit
- completedItems[]
- changedFiles[]
- verificationEvidence[]
- knownRisks[]
- nextSuggestedTasks[]
- ignoredSections[]
```

其中 `ignoredSections` 可用于标记某些只适用于特定工具或智能体的内容，避免接手方误读。

### 3.4 BaselineCheckTask：基线复核任务

跨智能体、跨会话接手前，第一步不应直接执行开发，而应先复核基线。

标准流程：

```text
拉取项目事实源
→ 读取文档导航 / 项目记忆 / 变更记录 / 交接包
→ 核对当前版本、任务流、最近 commit
→ 运行最小 QA
→ 输出基线复核结果
→ 再进入具体开发任务
```

建议把它作为标准任务类型，降低多智能体协作中的认知漂移。

## 4. 角色与执行者解耦

软件工厂不应把某个具体智能体绑定为固定角色。建议区分四层：

```text
Role（岗位）
  协同规划岗 / 实现验证岗 / 交付审查岗

Worker（执行者）
  某个具体智能体、人工、工具、自动化脚本

Workspace（工作空间）
  本地仓库、沙箱、远程容器、浏览器上下文

Artifact（产出）
  文档、代码、原型、QA 报告、截图、交接包
```

这样可以支持：

1. 同一岗位由不同执行者承担。
2. 同一执行者在不同任务中承担不同岗位。
3. 系统按职责、产出和验收标准调度，而不是按工具名称调度。

## 5. 建议的协作状态机（轻量版）

当前不建议直接实现完整复杂状态机，但可以先把协作过程抽象为轻量状态：

```text
DRAFTED
  设计侧已形成方案或任务，但尚未进入事实源。

COMMITTED
  产出已提交到项目仓库，可作为事实源。

BASELINE_CHECKED
  接手方已拉取、阅读关键文档并完成最小 QA。

IN_PROGRESS
  实施任务正在执行。

VERIFYING
  正在运行 QA / 截图 / 评审。

NEEDS_DECISION
  出现范围、设计、风险或验收分歧，需要用户或规划岗决策。

DONE
  已提交、推送、验证并更新项目记忆。
```

这个状态机不要求一次性改造现有前端，可以先用于任务单、交接包和项目记忆。

## 6. 对现有 v0.6.33 设计的补充建议

### 建议 A：在 SDD 中补充“外部工作空间与事实源”章节

说明不同智能体环境差异、Git 事实源原则、临时沙箱产物不作为事实源。

### 建议 B：在 WBS 中增加 BaselineCheckTask

每次新会话或跨智能体接手，先做基线复核，再选择开发任务。

### 建议 C：把 HandoffPackage 纳入任务流对象

交接文档不只是说明文字，应成为可解析、可追踪、可验证的任务产物。

### 建议 D：在原型中增加“工作空间 / 同步状态”轻量展示

不需要复杂页面，初期可在任务详情或团队成员详情里显示：

```text
工作空间类型：本地 / 沙箱 / 远程
同步方式：git / patch / 手动
最后同步 commit
当前产出是否已进入事实源
```

### 建议 E：把“角色可替换”写入产品原则

产品不绑定某个具体智能体、供应商或工具；只绑定职责、输入、输出、验收和同步协议。

---

## 7. 推荐优先级

| 优先级 | 建议 | 理由 |
|---|---|---|
| P0 | ProjectRepository 事实源原则 | 直接影响多智能体协作是否可信 |
| P0 | BaselineCheckTask | 降低接手误判和版本漂移 |
| P0 | HandoffPackage | 当前已经有真实样本，可快速标准化 |
| P1 | WorkerWorkspace | 为多 Runtime / 多工具协同打基础 |
| P1 | 原型展示同步状态 | 帮助用户理解谁在什么环境里做了什么 |

---

## 8. 建议写入产品愿景的一句话

> 智能软件工厂不是替代某一个智能体，而是管理多个智能体、人工和工具围绕同一项目事实源进行分工、交接、验证和持续推进的协作系统。

---

## 9. 对后续设计侧的建议

后续设计可优先围绕以下问题展开：

1. 如何在现有三岗位模型中挂接 WorkerWorkspace？
2. TaskTicket 与 HandoffPackage 的关系是父子关系、引用关系，还是同级 Artifact？
3. BaselineCheckTask 是所有任务流的强制前置节点，还是跨会话/跨 Worker 时才触发？
4. 前端原型是否需要增加“事实源状态 / 同步状态 / 最新 commit”轻量提示？
5. 哪些交接字段必须结构化，哪些可以保留自由文本？

这些问题解决后，当前人工协作方式就能更自然地沉淀为软件工厂的产品功能。
