# 多智能体协作产品化建议（v0.6.33）

> 目的：把当前“多个智能体 + 用户 + Git 仓库”协作推进 `agent-team` 项目的真实过程，整理为对 v0.6.33 PRD / SDD / ADR-0009 的增量建议与实践反馈。  
> 适用对象：后续设计侧智能体、实施侧智能体、项目负责人。  
> 版本口径：v0.6.33 / 原型 v0.6.33.45 / TF-P0B-05 后。

> 定位说明：本文不是替代现有 SDD / ADR 的新设计正本；涉及术语、状态和阶段划分时，应以现有 v0.6.33 PRD、SDD 与 ADR-0009 为准。本文只提供后续设计侧参考的补充建议。

---

## 0. 导读：本文核心建议概况

本文可概括为以下 7 条建议：

1. **任务单是软件工厂的核心锚点**  
   所有计划、执行、审查、决策、验收都应围绕 TaskTicket 展开；不要先追求多智能体聊天或复杂自动调度。

2. **当前多智能体协作就是软件工厂的真实样本**  
   把现在“设计侧、实施侧、用户、Git 仓库”协同推进项目的方式，产品化为软件工厂核心能力。

3. **Git 仓库是唯一事实源**  
   聊天记录、沙箱文件都不是最终事实；只有进入仓库的 `docs/`、`apps/`、QA 报告和交接文档才算有效产物。

4. **角色、执行者、工作空间、产物要解耦**  
   岗位不绑定具体智能体；同一岗位可由不同 AI、人工或工具承担，系统只管理职责、产出和验收。

5. **跨智能体接手前必须做基线复核**  
   拉取仓库、读取文档导航 / 项目记忆 / 变更记录、核对版本、运行最小 QA，再开始具体任务，避免基线漂移。

6. **设计侧和实施侧要双向同步**  
   设计产物要同步给实施侧；实施结果、QA 问题、工程约束和用户验收结论也要反向同步给设计侧。

7. **交接包要逐步结构化**  
   交接不只写“做了什么”，还要记录验证证据、风险、下一步和关键决策理由，未来可发展成系统对象。

## 1. 核心判断

当前 `agent-team` 的研发方式，本身就是智能软件工厂的第一批真实业务样本。

```text
当前真实协作：
  设计侧智能体产出 PRD / SDD / 任务流 / 原型 / 交接文档
  实施侧智能体落盘代码 / 跑 QA / 提交 git / 更新项目记忆
  用户负责触发同步、验收和关键决策
  Git 仓库承载最终事实

产品化目标：
  软件工厂把以上人工协调动作系统化、可追踪、可验证、可恢复。
```

因此，建议把“当前人工多智能体协作链路”明确纳入产品设计，不只作为临时开发流程。

---

## 2. 当前实践到产品能力的映射

| 当前实践 | 产品化能力 |
|---|---|
| 设计侧智能体输出 PRD、SDD、原型、任务流 | 协同规划岗：需求沉淀、方案设计、任务拆解 |
| 实施侧智能体编码、测试、提交 | 实现验证岗：任务执行、验证、回执 |
| 用户验收、决策仲裁 | 待决策机制 + 交付审查岗 |
| 当前协作依赖“用户口头任务 + 文档清单”驱动 | TaskTicket First：计划、执行、审查、决策、验收都围绕任务单沉淀 |
| Git 仓库作为最终事实源 | ProjectRepository / Artifact Store |
| docs/ 与 apps/ 作为交接契约 | TaskTicket / WorkOrder / Artifact / Evidence |
| handoff/update 文档说明当前状态 | HandoffPackage / BaselineSnapshot |
| 实施前先 pull、读文档、跑 QA | BaselineCheckTask |
| 发现设计缺口后反馈，不擅自改设计 | ChangeRequest / DecisionItem |
| 设计推理与取舍散落在聊天记录中，接手方不可见 | DecisionContext / DesignRationale：关键 why 随 Artifact 沉淀 |

## 3. 建议补充的核心产品对象

### 3.0 TaskTicket First：任务单优先原则

软件工厂当前阶段不应先做多智能体自由聊天、复杂自动调度或完整状态机。应先把所有协作收敛到 TaskTicket：

```text
计划
→ TaskTicket
→ 执行回执 / TaskEvent / ExecutionResult
→ ReviewRecord
→ DecisionItem / ChangeRequest
→ AcceptanceRecord / ReworkOrder
→ Activity 回写
```

TaskTicket 是其他对象的挂载点：

```text
Workspace 服务哪个任务
Artifact 归属哪个任务
HandoffPackage 交接哪个任务流或任务集合
BaselineCheckTask 为哪个任务接手前复核
Review / Decision / Acceptance 审查和确认哪个任务
```

P0 阶段的任务单不需要很复杂，但至少应包含：

```text
- taskId
- title / goal
- ownerRole / ownerWorker
- inputArtifacts[]
- outputArtifacts[]
- status
- verificationEvidence[]
- decisionItems[]
- nextAction
```

关键原则：可以聊天、讨论和临时探索，但关键结论必须回写到 TaskTicket、Artifact、ReviewRecord、DecisionItem 或 AcceptanceRecord 中，不能只停留在聊天上下文。

### 3.1 Workspace：外部工作空间（阶段 D 概念的提前需求输入）

不同智能体可能运行在不同环境中：本地持久工作区、云端沙箱、浏览器会话、远程容器等。产品需要显式建模工作空间，而不是假设所有 Worker 都在同一运行环境。

命名对齐：SDD 中已有阶段 D 的 `Workspace / RuntimeHost / RuntimeNode` 方向，本文不再新建平行术语 `WorkerWorkspace`。这里的 `Workspace` 是从当前真实协作中提炼出的需求输入，应在后续阶段 D 建模时并入 SDD 既有概念。

建议字段：

```text
Workspace
- workspaceId
- workerId
- projectId
- sourceType: local / sandbox / remote / browser-only
- syncMethod: git / patch / zip / manual
- persistence: persistent / ephemeral
- readableScopes: docs / apps / prototypes / reports
- writableScopes: docs / apps / reports / none
- lastSyncedCommit
```

价值：

1. 解释“为什么有的智能体能直接改代码，有的只能产出文档包”。
2. 让系统知道某个产出是否已进入事实源。
3. 为后续多 Runtime 调度、权限隔离和恢复提供基础。

### 3.2 ProjectRepository：项目事实源

当前协作里，聊天内容不是事实源，Git 仓库才是事实源。

这条原则在现有项目记忆与协作规范中已经基本成立；本文建议把它作为产品原则继续强化，而不是在当前阶段 A 立即新增复杂系统实现。

建议原则：

```text
ProjectRepository = 项目事实源
Conversation = 过程上下文
Sandbox File = 临时产物
Committed Artifact = 有效产物
```

产品上最终需要把“是否已落盘到仓库 / 是否对应 commit / 是否通过 QA”纳入任务证据。当前 P0 阶段可先以人工检查与 BaselineCheckTask 的形式执行，不要求立即做完整 Artifact Store。

同时建议区分 Artifact 的可信度层级，避免把“已提交”误认为“已验证”或“已验收”：

```text
Committed
  已进入 ProjectRepository，但尚未完成验证。

Verified
  已通过自动化 QA、截图检查、人工复核或交付审查中的一种或多种。

Accepted
  已被用户、协同规划岗或交付审查岗确认可作为当前基线。
```

P0 阶段不需要实现复杂的 Artifact Store，但 BaselineCheckTask 和交接文档应尽量说明关键产物处于哪个可信度层级。

### 3.3 HandoffPackage：交接包

`update/HANDOFF-*.md` 这类文档应被抽象为一等对象，而不是自由文本附件。

阶段定位：当前可继续使用 Markdown 交接文档作为人工约定；结构化解析、存储和校验属于 P1 或 Guarded Task Flow 之后的工作，不建议在当前 Agent-led Task List 阶段强行实现。

建议结构：

```text
HandoffPackage
- packageId
- projectId
- baselineVersion
- taskflowId
- sourceCommit
- completedItems[]
- changedFiles[]
- verificationEvidence[]
- knownRisks[]
- decisionRationale[]
- nextSuggestedTasks[]
- ignoredSections[]
```

其中 `ignoredSections` 可用于标记某些只适用于特定工具或智能体的内容，避免接手方误读。

`decisionRationale[]` 用于沉淀关键取舍：为什么选择当前方案、排除了哪些方案、有哪些已知坑不要重复踩。它不需要记录完整思维过程，但应记录足以支持后续接手者理解设计意图的关键依据。

### 3.4 BaselineCheckTask：基线复核任务

跨智能体、跨会话接手前，第一步不应直接执行开发，而应先复核基线。

标准流程：

```text
拉取项目事实源
→ 读取文档导航 / 项目记忆 / 变更记录 / 交接包
→ 核对当前版本、任务流、最近 commit
→ 校验关键版本声明是否一致或差异可解释
→ 运行最小 QA
→ 输出基线复核结果
→ 再进入具体开发任务
```

建议把它作为标准任务类型，降低多智能体协作中的认知漂移。

这是本文建议中最适合 P0 立即落地的部分：不需要新增复杂数据模型，只需要把“接手前先复核事实源”的步骤标准化为任务流前置节点。

建议的版本漂移校验项：

```text
- docs/文档导航.md 中声明的当前基线
- docs/project-memory.md 中声明的当前版本
- README.md 中声明的当前同步批次
- apps/web/README.md 中声明的 apps/web 基线
- docs/prototypes/ 中最新原型文件名与内容版本
- docs/changes/CHANGELOG-v0.6.33.md 最新条目
```

允许存在“文档基线 v0.6.33 / 原型基线 v0.6.33.45 / 任务流基线 TF-P0B-05”这类可解释差异，但必须显式说明。不能出现无解释的旧版本引用、死链或缺失文件。

BaselineCheckTask 失败时建议按以下方式处理：

```text
发现不一致 / QA 失败 / 文件缺失
→ 判断是否属于接手方可安全修复的问题
  → 是：最小修复 → 提交 → 重跑 BaselineCheckTask → 输出修复记录
  → 否：生成 DecisionItem / ChangeRequest → 暂停具体开发任务 → 等待设计侧或用户决策
```

这样 BaselineCheckTask 不只是“检查清单”，而是一个有失败处置路径的标准任务。

示例：接手方执行 BaselineCheckTask 时发现 `docs/文档导航.md` 引用了已删除文件，且不涉及产品决策或架构取舍。这属于可安全修复的问题。接手方可以直接更新导航、提交修改、重跑基线复核，然后再进入具体开发任务。若发现的是版本基线冲突、原型口径冲突或任务范围变化，则应生成 DecisionItem / ChangeRequest，暂停具体开发任务等待确认。

### 3.5 DesignImplementationSync：设计-实施双向同步协议

当前最容易出问题的不是单个智能体能力，而是设计侧与实施侧之间的同步节奏：设计侧可能已经在沙箱中更新，实施侧却仍以旧仓库为准；或实施侧已经修复并推送，设计侧仍参考旧原型。

建议把“设计→实施”的同步协议产品化：

```text
设计侧提交产物
→ 产物进入 ProjectRepository
→ 生成或更新 HandoffPackage / ChangeLog
→ 实施侧收到接手信号
→ 执行 BaselineCheckTask
→ 输出接手确认回执
→ 进入具体 TaskTicket
```

P0 可落地为人工流程与文档模板；P1 再考虑自动检测 docs/apps 变更、触发通知和接手确认。

同时需要补充“实施→设计”的反向同步协议：

```text
实施侧完成任务并推送
→ 更新 CHANGELOG / project-memory / QA 报告 / 交付说明
→ 产物进入 ProjectRepository
→ 设计侧收到事实源变更信号
→ 设计侧执行轻量 BaselineCheckTask 或读取最新交接信息
→ 基于最新事实源继续设计，而不是沿用旧沙箱副本
```

反向同步是软件工厂真实运转的关键：实现结果、验证失败、工程约束和用户验收结论都会反过来影响后续设计。

## 4. 角色与执行者解耦

软件工厂不应把某个具体智能体绑定为固定角色。建议区分四层：

```text
Role（岗位）
  协同规划岗 / 实现验证岗 / 交付审查岗

Worker（执行者）
  某个具体智能体、人工、工具、自动化脚本

Workspace（工作空间）
  本地仓库、沙箱、远程容器、浏览器上下文

Artifact（产出）
  文档、代码、原型、QA 报告、截图、交接包
```

与现有三岗位模型的关系：

```text
PRD / SDD 中的三岗位
  = Role 层的核心岗位实例：协同规划岗、实现验证岗、交付审查岗。

数字员工 / 外部智能体 / 人工执行者
  = Worker 层，负责实际完成某个 Role 下的任务。

本地仓库 / 云端沙箱 / 远程环境
  = Workspace 层，是 Worker 的执行环境与同步边界。

文档 / 代码 / QA 报告 / 交接包
  = Artifact 层，是任务验收和跨会话交接的证据。
```

这样可以支持：

1. 同一岗位由不同执行者承担。
2. 同一执行者在不同任务中承担不同岗位。
3. 系统按职责、产出和验收标准调度，而不是按工具名称调度。

后续 Workspace / Worker 建模还应记录能力边界，例如是否能直接 git push、是否能运行测试、是否能做浏览器验证、会话是否持久、上下文窗口是否足够处理大文档等。当前文档只提出需求输入，具体字段应在阶段 D 设计中与 RuntimeHost / RuntimeNode 统一建模。

## 5. 对现有任务状态的补充检查点

当前不建议直接实现完整复杂状态机，也不建议另起一套与 SDD 冲突的状态机。SDD 中已有主线状态：

```text
TODO → RUNNING → REVIEWING → NEEDS_DECISION → DONE
```

本文建议只在这条主线之外补充“检查点 / 事件 / 证据”，而不是替换状态定义：

```text
DRAFTED
  设计侧已形成方案或任务，但尚未进入事实源。可作为 TaskEvent / Artifact 状态。

COMMITTED
  产出已提交到项目仓库，可作为事实源。对应 commit / artifact evidence。

BASELINE_CHECKED
  接手方已拉取、阅读关键文档并完成最小 QA。建议作为 TaskTicket 进入 RUNNING 前的前置检查。

VERIFYING
  正在运行 QA / 截图 / 评审。可映射到 SDD 的 REVIEWING 或 ReviewRecord。
```

其中 `BASELINE_CHECKED` 是最有价值的新增检查点，建议优先纳入 WBS / taskflow，而不是升级为新的主状态。

## 6. 对现有 v0.6.33 设计的补充建议

### 建议 A：在 SDD 中补充“外部工作空间与事实源”章节

说明不同智能体环境差异、Git 事实源原则、临时沙箱产物不作为事实源。注意应复用 SDD 中已有的 `Workspace / RuntimeHost / RuntimeNode` 方向，不另造平行概念。

### 建议 B：在 WBS 中增加 BaselineCheckTask

每次新会话或跨智能体接手，先做基线复核，再选择开发任务。

BaselineCheckTask 应包含版本漂移检测和失败处置路径：可安全修复的问题由接手方最小修复并提交；不可安全修复的问题生成 DecisionItem / ChangeRequest。

### 建议 C：把 HandoffPackage 纳入任务流对象

交接文档不只是说明文字，应逐步成为可解析、可追踪、可验证的任务产物。当前阶段可先规范 Markdown 结构；结构化解析和系统存储放到 P1。

交接文档中建议增加 `decisionRationale` 区块，用于记录关键取舍、排除方案和已知坑，避免不同智能体反复重新推理。

### 建议 D：在原型中增加“工作空间 / 同步状态”轻量展示

这项不建议进入当前 P0B 立即开发。等 data-provider / mock 数据进一步收口后，可在任务详情或团队成员详情里轻量展示：

```text
工作空间类型：本地 / 沙箱 / 远程
同步方式：git / patch / 手动
最后同步 commit
当前产出是否已进入事实源
```

### 建议 E：把“角色可替换”写入产品原则

产品不绑定某个具体智能体、供应商或工具；只绑定职责、输入、输出、验收和同步协议。

### 建议 F：补充“设计-实施双向同步协议”

把当前人工执行的“设计侧提交 → 用户通知 → 实施侧 pull → 基线复核 → 接手确认”沉淀为标准流程，并补充“实施侧推送 → 更新项目记忆/变更记录/QA → 设计侧拉取最新事实源”的反向流程。P0 先用文档和任务流约定，P1 再做自动通知和状态追踪。

### 建议 G：补充 Artifact 可信度分层

把 Committed / Verified / Accepted 作为产物状态或证据标签，避免“已提交”被误解为“已验证”或“已验收”。P0 只需在交接文档和 BaselineCheckTask 输出中显式标注，不需要新增复杂存储。

## 7. 当前阶段不建议做的事

为避免把建议误解为立即进入复杂系统实现，当前 Agent-led Task List / P0B 阶段不建议做以下事项：

```text
1. 不实现完整 Artifact Store 数据库。
   当前只需在交接文档、QA 报告和 BaselineCheckTask 输出中标注证据与可信度。

2. 不实现自动通知系统。
   设计-实施同步先通过 git、文档和人工通知完成；后续再考虑自动检测和提醒。

3. 不实现文件级锁或复杂并发控制。
   当前先通过任务边界、目录分工和人工约定避免冲突。

4. 不实现完整 Workspace / Runtime 调度。
   Workspace 仅作为阶段 D 的需求输入；当前不做运行时编排。

5. 不把 HandoffPackage 立即做成强结构化系统对象。
   当前先规范 Markdown 结构，保留必要自由文本，后续再逐步结构化。

6. 不绕过 TaskTicket 做自由聊天式协作。
   聊天可以存在，但关键结论、执行结果、审查意见和待决策项必须回写任务单或关联记录。
```

## 8. 推荐优先级

| 优先级 | 建议 | 理由 |
|---|---|---|
| P0 | TaskTicket First | 所有协作围绕任务单沉淀，是后续状态机、Runtime 调度和验收门禁的基础 |
| P0 | BaselineCheckTask | 不依赖复杂系统实现，可立即降低接手误判和版本漂移 |
| P0 原则 | ProjectRepository 事实源原则 | 当前先作为必须遵守的协作原则，不急于做完整 Artifact Store |
| P0 流程 | DesignImplementationSync 双向人工流程 | 解决设计侧/实施侧双向同步痛点，可先用文档和任务流约定 |
| P0 证据标签 | Artifact 可信度分层 | 用 Committed / Verified / Accepted 区分产物可信度，避免误判 |
| P1 | HandoffPackage 结构化 | 当前已有 Markdown 样本，但解析/存储/校验需要后续基础设施 |
| P1 / 阶段 D 预研 | Workspace 建模 | 应并入 SDD 阶段 D 的 Workspace / RuntimeHost / RuntimeNode 体系 |
| P1 后期 | 原型展示同步状态 | 需等 data-provider / mock 数据进一步收口后再做 |

---

## 9. 建议写入产品愿景的一句话

> 智能软件工厂的关键增量，是把异构智能体、人工和工具在不同工作空间中的产出，统一纳入同一个项目事实源、任务闭环和验收门禁。

## 10. 对后续设计侧的建议

后续设计可优先围绕以下问题展开：

### 10.1 建议优先回答

1. TaskTicket 的 P0 最小字段集是什么？哪些字段必须当前阶段就有，哪些可以 P1 再扩展？
2. BaselineCheckTask 是所有任务流的强制前置节点，还是只在跨会话 / 跨 Worker / 跨工作空间时触发？
3. TaskTicket 与 HandoffPackage 的关系是父子关系、引用关系，还是同级 Artifact？
4. 设计-实施同步协议应由用户手动触发、Git 变更触发，还是由任务流状态触发？
5. Artifact 的 Committed / Verified / Accepted 三层是否足够，是否需要更细的证据类型？
6. `project-memory.md` 被多方写入时，是否需要分区、合并策略或审查门禁？

### 10.2 后续讨论

7. 如何把本文的 Workspace 需求并入 SDD 阶段 D 的 Workspace / RuntimeHost / RuntimeNode 概念？
8. 反向同步中，实施侧发现的工程约束、QA 失败和用户验收结论应如何回写给设计侧？
9. 前端原型是否需要增加“事实源状态 / 同步状态 / 最新 commit”轻量提示？如果需要，应放在 P1 的哪个阶段？
10. 哪些交接字段必须结构化，哪些可以保留自由文本？
11. 当设计侧和实施侧并行工作时，如何避免双方基于不同版本产出冲突？
12. 是否需要任务级或文件级锁，防止多个 Worker 同时修改同一批关键文档或代码？

这些问题解决后，当前人工协作方式就能更自然地沉淀为软件工厂的产品功能。
