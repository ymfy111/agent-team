# 多智能体协作产品化建议（v0.6.33）

> 目的：把当前“多个智能体 + 用户 + Git 仓库”协作推进 `agent-team` 项目的真实过程，整理为对 v0.6.33 PRD / SDD / ADR-0009 的增量建议与实践反馈。  
> 适用对象：后续设计侧智能体、实施侧智能体、项目负责人。  
> 版本口径：v0.6.33 / 原型 v0.6.33.45 / TF-P0B-05 后。

> 定位说明：本文不是替代现有 SDD / ADR 的新设计正本；涉及术语、状态和阶段划分时，应以现有 v0.6.33 PRD、SDD 与 ADR-0009 为准。本文只提供后续设计侧参考的补充建议。

---

## 1. 核心判断

当前 `agent-team` 的研发方式，本身就是智能软件工厂的第一批真实业务样本。

```text
当前真实协作：
  设计侧智能体产出 PRD / SDD / 任务流 / 原型 / 交接文档
  实施侧智能体落盘代码 / 跑 QA / 提交 git / 更新项目记忆
  用户负责触发同步、验收和关键决策
  Git 仓库承载最终事实

产品化目标：
  软件工厂把以上人工协调动作系统化、可追踪、可验证、可恢复。
```

因此，建议把“当前人工多智能体协作链路”明确纳入产品设计，不只作为临时开发流程。

---

## 2. 当前实践到产品能力的映射

| 当前实践 | 产品化能力 |
|---|---|
| 设计侧智能体输出 PRD、SDD、原型、任务流 | 协同规划岗：需求沉淀、方案设计、任务拆解 |
| 实施侧智能体编码、测试、提交 | 实现验证岗：任务执行、验证、回执 |
| 用户验收、决策仲裁 | 待决策机制 + 交付审查岗 |
| Git 仓库作为最终事实源 | ProjectRepository / Artifact Store |
| docs/ 与 apps/ 作为交接契约 | TaskTicket / WorkOrder / Artifact / Evidence |
| handoff/update 文档说明当前状态 | HandoffPackage / BaselineSnapshot |
| 实施前先 pull、读文档、跑 QA | BaselineCheckTask |
| 发现设计缺口后反馈，不擅自改设计 | ChangeRequest / DecisionItem |

---

## 3. 建议补充的核心产品对象

### 3.1 Workspace：外部工作空间（阶段 D 概念的提前需求输入）

不同智能体可能运行在不同环境中：本地持久工作区、云端沙箱、浏览器会话、远程容器等。产品需要显式建模工作空间，而不是假设所有 Worker 都在同一运行环境。

命名对齐：SDD 中已有阶段 D 的 `Workspace / RuntimeHost / RuntimeNode` 方向，本文不再新建平行术语 `WorkerWorkspace`。这里的 `Workspace` 是从当前真实协作中提炼出的需求输入，应在后续阶段 D 建模时并入 SDD 既有概念。

建议字段：

```text
Workspace
- workspaceId
- workerId
- projectId
- sourceType: local / sandbox / remote / browser-only
- syncMethod: git / patch / zip / manual
- persistence: persistent / ephemeral
- readableScopes: docs / apps / prototypes / reports
- writableScopes: docs / apps / reports / none
- lastSyncedCommit
```

价值：

1. 解释“为什么有的智能体能直接改代码，有的只能产出文档包”。
2. 让系统知道某个产出是否已进入事实源。
3. 为后续多 Runtime 调度、权限隔离和恢复提供基础。

### 3.2 ProjectRepository：项目事实源

当前协作里，聊天内容不是事实源，Git 仓库才是事实源。

这条原则在现有项目记忆与协作规范中已经基本成立；本文建议把它作为产品原则继续强化，而不是在当前阶段 A 立即新增复杂系统实现。

建议原则：

```text
ProjectRepository = 项目事实源
Conversation = 过程上下文
Sandbox File = 临时产物
Committed Artifact = 有效产物
```

产品上最终需要把“是否已落盘到仓库 / 是否对应 commit / 是否通过 QA”纳入任务证据。当前 P0 阶段可先以人工检查与 BaselineCheckTask 的形式执行，不要求立即做完整 Artifact Store。

### 3.3 HandoffPackage：交接包

`update/HANDOFF-*.md` 这类文档应被抽象为一等对象，而不是自由文本附件。

阶段定位：当前可继续使用 Markdown 交接文档作为人工约定；结构化解析、存储和校验属于 P1 或 Guarded Task Flow 之后的工作，不建议在当前 Agent-led Task List 阶段强行实现。

建议结构：

```text
HandoffPackage
- packageId
- projectId
- baselineVersion
- taskflowId
- sourceCommit
- completedItems[]
- changedFiles[]
- verificationEvidence[]
- knownRisks[]
- nextSuggestedTasks[]
- ignoredSections[]
```

其中 `ignoredSections` 可用于标记某些只适用于特定工具或智能体的内容，避免接手方误读。

### 3.4 BaselineCheckTask：基线复核任务

跨智能体、跨会话接手前，第一步不应直接执行开发，而应先复核基线。

标准流程：

```text
拉取项目事实源
→ 读取文档导航 / 项目记忆 / 变更记录 / 交接包
→ 核对当前版本、任务流、最近 commit
→ 运行最小 QA
→ 输出基线复核结果
→ 再进入具体开发任务
```

建议把它作为标准任务类型，降低多智能体协作中的认知漂移。

这是本文建议中最适合 P0 立即落地的部分：不需要新增复杂数据模型，只需要把“接手前先复核事实源”的步骤标准化为任务流前置节点。

### 3.5 DesignImplementationSync：设计-实施同步协议

当前最容易出问题的不是单个智能体能力，而是设计侧与实施侧之间的同步节奏：设计侧可能已经在沙箱中更新，实施侧却仍以旧仓库为准；或实施侧已经修复并推送，设计侧仍参考旧原型。

建议把“设计→实施”的同步协议产品化：

```text
设计侧提交产物
→ 产物进入 ProjectRepository
→ 生成或更新 HandoffPackage / ChangeLog
→ 实施侧收到接手信号
→ 执行 BaselineCheckTask
→ 输出接手确认回执
→ 进入具体 TaskTicket
```

P0 可落地为人工流程与文档模板；P1 再考虑自动检测 docs/apps 变更、触发通知和接手确认。

## 4. 角色与执行者解耦

软件工厂不应把某个具体智能体绑定为固定角色。建议区分四层：

```text
Role（岗位）
  协同规划岗 / 实现验证岗 / 交付审查岗

Worker（执行者）
  某个具体智能体、人工、工具、自动化脚本

Workspace（工作空间）
  本地仓库、沙箱、远程容器、浏览器上下文

Artifact（产出）
  文档、代码、原型、QA 报告、截图、交接包
```

与现有三岗位模型的关系：

```text
PRD / SDD 中的三岗位
  = Role 层的核心岗位实例：协同规划岗、实现验证岗、交付审查岗。

数字员工 / 外部智能体 / 人工执行者
  = Worker 层，负责实际完成某个 Role 下的任务。

本地仓库 / 云端沙箱 / 远程环境
  = Workspace 层，是 Worker 的执行环境与同步边界。

文档 / 代码 / QA 报告 / 交接包
  = Artifact 层，是任务验收和跨会话交接的证据。
```

这样可以支持：

1. 同一岗位由不同执行者承担。
2. 同一执行者在不同任务中承担不同岗位。
3. 系统按职责、产出和验收标准调度，而不是按工具名称调度。

## 5. 对现有任务状态的补充检查点

当前不建议直接实现完整复杂状态机，也不建议另起一套与 SDD 冲突的状态机。SDD 中已有主线状态：

```text
TODO → RUNNING → REVIEWING → NEEDS_DECISION → DONE
```

本文建议只在这条主线之外补充“检查点 / 事件 / 证据”，而不是替换状态定义：

```text
DRAFTED
  设计侧已形成方案或任务，但尚未进入事实源。可作为 TaskEvent / Artifact 状态。

COMMITTED
  产出已提交到项目仓库，可作为事实源。对应 commit / artifact evidence。

BASELINE_CHECKED
  接手方已拉取、阅读关键文档并完成最小 QA。建议作为 TaskTicket 进入 RUNNING 前的前置检查。

VERIFYING
  正在运行 QA / 截图 / 评审。可映射到 SDD 的 REVIEWING 或 ReviewRecord。
```

其中 `BASELINE_CHECKED` 是最有价值的新增检查点，建议优先纳入 WBS / taskflow，而不是升级为新的主状态。

## 6. 对现有 v0.6.33 设计的补充建议

### 建议 A：在 SDD 中补充“外部工作空间与事实源”章节

说明不同智能体环境差异、Git 事实源原则、临时沙箱产物不作为事实源。注意应复用 SDD 中已有的 `Workspace / RuntimeHost / RuntimeNode` 方向，不另造平行概念。

### 建议 B：在 WBS 中增加 BaselineCheckTask

每次新会话或跨智能体接手，先做基线复核，再选择开发任务。

### 建议 C：把 HandoffPackage 纳入任务流对象

交接文档不只是说明文字，应逐步成为可解析、可追踪、可验证的任务产物。当前阶段可先规范 Markdown 结构；结构化解析和系统存储放到 P1。

### 建议 D：在原型中增加“工作空间 / 同步状态”轻量展示

这项不建议进入当前 P0B 立即开发。等 data-provider / mock 数据进一步收口后，可在任务详情或团队成员详情里轻量展示：

```text
工作空间类型：本地 / 沙箱 / 远程
同步方式：git / patch / 手动
最后同步 commit
当前产出是否已进入事实源
```

### 建议 E：把“角色可替换”写入产品原则

产品不绑定某个具体智能体、供应商或工具；只绑定职责、输入、输出、验收和同步协议。

### 建议 F：补充“设计-实施同步协议”

把当前人工执行的“设计侧提交 → 用户通知 → 实施侧 pull → 基线复核 → 接手确认”沉淀为标准流程。P0 先用文档和任务流约定，P1 再做自动通知和状态追踪。

---

## 7. 推荐优先级

| 优先级 | 建议 | 理由 |
|---|---|---|
| P0 | BaselineCheckTask | 不依赖复杂系统实现，可立即降低接手误判和版本漂移 |
| P0 原则 | ProjectRepository 事实源原则 | 当前先作为必须遵守的协作原则，不急于做完整 Artifact Store |
| P0 流程 | DesignImplementationSync 人工流程 | 解决当前设计侧/实施侧同步痛点，可先用文档和任务流约定 |
| P1 | HandoffPackage 结构化 | 当前已有 Markdown 样本，但解析/存储/校验需要后续基础设施 |
| P1 / 阶段 D 预研 | Workspace 建模 | 应并入 SDD 阶段 D 的 Workspace / RuntimeHost / RuntimeNode 体系 |
| P1 后期 | 原型展示同步状态 | 需等 data-provider / mock 数据进一步收口后再做 |

---

## 8. 建议写入产品愿景的一句话

> 智能软件工厂的关键增量，是把异构智能体、人工和工具在不同工作空间中的产出，统一纳入同一个项目事实源、任务闭环和验收门禁。

---

## 9. 对后续设计侧的建议

后续设计可优先围绕以下问题展开：

1. 如何把本文的 Workspace 需求并入 SDD 阶段 D 的 Workspace / RuntimeHost / RuntimeNode 概念？
2. TaskTicket 与 HandoffPackage 的关系是父子关系、引用关系，还是同级 Artifact？
3. BaselineCheckTask 是所有任务流的强制前置节点，还是只在跨会话 / 跨 Worker / 跨工作空间时触发？
4. 设计-实施同步协议应由用户手动触发、Git 变更触发，还是由任务流状态触发？
5. 前端原型是否需要增加“事实源状态 / 同步状态 / 最新 commit”轻量提示？如果需要，应放在 P1 的哪个阶段？
6. 哪些交接字段必须结构化，哪些可以保留自由文本？

这些问题解决后，当前人工协作方式就能更自然地沉淀为软件工厂的产品功能。
