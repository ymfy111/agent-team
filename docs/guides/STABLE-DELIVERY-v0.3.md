# 稳交付 / Stable Delivery v0.3 指南

> 用途：记录后续原型、文档、补丁迭代的默认执行闭环。  
> 触发口径：用户说“任务执行”时进入标准模式；用户说“任务执行 高质量”时进入高质量模式。

## 1. 核心目标

稳交付不是为了增加流程负担，而是为了避免：

```text
一次改太多
改坏已封板区域
只做 DOM 检查不看视觉效果
独立评审流于形式
交付后用户难以比较前后效果
```

## 2. 标准流程

```text
说明并确认计划
→ minimax 小步修改
→ 快速验证与截图自查
→ 独立评审
→ 评审追踪表
→ 必要修复
→ 再验证
→ 前后截图对比
→ 用户验收
→ 验收通过后进入下一阶段
```

## 3. 执行模式

| 模式 | 触发词 | 评审要求 | 适用场景 |
|---|---|---|---|
| standard | 任务执行 | 至少 1 轮独立评审；本轮范围内 P0/P1/P2 必须修复 | 普通补丁、阶段推进 |
| high-quality | 任务执行 高质量 | 至少 2 轮评审，最多 4 轮；按问题收敛决定是否继续 | 关键页面、验收、最终收口 |
| hotfix | 只修这个问题 / 安全补丁 | 只围绕明确问题和冻结项评审 | 回归修复、紧急补丁 |

## 4. 每轮开工前必须说明

```text
当前基线
目标版本
本轮任务
实施步骤
冻结项
验收标准
预计产物
```

## 5. 独立评审必须落实为实际动作

独立评审应基于产物、截图、验证结果和冻结项，从以下维度检查：

```text
产品视角：是否解决本轮主问题
交互视角：用户是否能理解和操作
视觉视角：是否过空、过挤、过花、层级混乱
实现视角：是否只改本轮范围，是否破坏封板区域
风险视角：是否有刷新不一致、旧逻辑回退、入口失效、数据口径不一致
```

## 6. 评审追踪表

每次交付应包含：

| 评审发现 | 级别 | 处理决定 | 实际修改 | 状态 |
|---|---:|---|---|---|
| 示例问题 | P1 | 本轮修复 | 已做最小修改 | 已关闭 |

## 7. 截图要求

原型 / UI 任务必须提供：

```text
修改前截图
修改后截图
前后横向对比图
冻结验证截图
```

涉及多个页面时，应提供关键页面对比图。

## 8. 完成后必须说明

```text
完成情况
验证结果
独立评审结论
评审发现与处理追踪
未改范围
下一步建议
是否等待用户验收
```

## 9. 基线规则

```text
验收通过后，当前版本才成为新安全基线。
验收不通过时，不应在坏版本上继续叠补丁；应回到最近安全基线或明确修复版。
用户中途提出的新问题，不默认混入当前小版本，先记录为下一轮待办。
```
