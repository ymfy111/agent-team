## 0. 计划目标

本计划用于组织 DEOS v0.7 后续子设计。为避免文档再次碎片化，本版采用**少数主子设计 + 章节承载细分内容**的方式，不再把能力契约、安全、人机协同、本体回流等全部拆成独立文档。

目标：

1. 明确 DEOS 当前需要优先补齐的主子设计。
2. 明确每份主子设计包含哪些章节，避免拆得过细。
3. 明确 M1–M4 推进顺序，先做运行平台，再做管理/运营平台和业务系统集成。
4. 明确旧 agent-team 文档仅作历史参考，新设计直接面向 DEOS v0.7。

## 3. 各主子设计章节范围

### 3.1 数字员工运行平台

文件：`docs/specs/SDD-DE-RUNTIME-PLATFORM-v0.7.md`

包含章节：

- 运行支撑边界：动态工作流引擎、任务调度/编排、服务注册/发现。
- 两类数字员工运行入口：构建型版本制、应用型任务制。
- 应用型数字员工运行时：`AppTask / AppSession / Step / Checkpoint`。
- 能力库调用契约：发现、调用、权限、版本、超时、审计。
- 人机协同检查点：确认、审批、干预、接管。
- 运行事件与可观测：`RuntimeTaskEnvelope / RuntimeSession / RuntimeEvent`。
- 运行平台安全基线：最小授权、代执行边界、审计。
- 本体回流最小接口：运行事件如何进入本体回流链路。

不包含：能力库高级治理、管理平台页面、运营看板、业务系统连接器、应用侧 UI。

### 3.2 数字员工管理平台

## 4. 分期计划

### M1：数字员工运行平台

目标：形成 DEOS 的运行支撑底座，并把应用型数字员工运行时作为章节纳入。

Done 条件（运行平台对外契约封口）：

- 明确运行平台 = 2F 运行支撑，不含能力库。
- 定义动态工作流引擎、任务调度/编排、服务注册/发现边界。
- 定义 `RuntimeEvent` 字段与运营指标映射，支撑运营平台消费。
- 定义 `AppTask → RuntimeTaskEnvelope → RuntimeSession` 转换图。
- 定义应用型任务制状态机与 `RuntimeSession.status` 映射表。
- 定义 Checkpoint 协议：确认、审批、干预、接管。
- 定义能力调用契约最小字段：能力引用、版本、入参、授权上下文、超时、审计账本。

### M2：数字员工管理平台 + 数字员工运营平台

目标：让两类数字员工可被管理、可被运营。

Done 条件：

- 管理平台明确权限、岗位、技能、团队、配置管理对象。
- 运营平台明确运行监控、成本、告警、调优指标。
- 两个平台都引用 M1 的运行对象和运行事件，不自造运行模型。

### M3：业务系统集成

目标：让应用型数字员工能与真实业务系统协同。

Done 条件：

- 明确 API / 消息 / RPA 三类集成模式。
- 明确入站触发与出站调用。
- 明确权限边界、数据主权和连接器抽象。

### M4：按复杂度再拆

目标：当能力库治理、本体回流、应用侧终端复杂度上升时，再决定是否独立成文。

当前处理：

- 能力库治理先作为运行平台和运营平台章节。
- 本体回流先作为运行平台和运营平台章节。
- 应用侧终端先作为运营平台章节。

## 5. 关键依赖

```text
SDD-DE-RUNTIME-PLATFORM
  ├─ SDD-DE-MANAGEMENT-PLATFORM
  ├─ SDD-DE-OPERATIONS-PLATFORM
  └─ SDD-BIZ-SYSTEM-INTEGRATION
```

依赖解释：

- 管理平台需要知道数字员工实例如何绑定运行平台。
- 运营平台需要消费运行平台输出的运行事件和指标。
- 业务系统集成需要通过运行平台触发或承载应用型数字员工任务。

## 6. 命名与归属规则

1. 所有主子设计使用 `v0.7` 后缀。
2. 所有新设计直接归入 DEOS，不再挂靠旧 agent-team 主 SDD。
3. `SDD-APPLICATION-DE-v0.7.md` 是应用侧概述与索引，不再维护独立子设计命名空间。
4. 能力库、人机协同、安全、本体回流、应用侧终端先作为主子设计章节，暂不独立成文档。
5. 若某个章节后续超过单文档可控范围，再升级为独立 SDD。
