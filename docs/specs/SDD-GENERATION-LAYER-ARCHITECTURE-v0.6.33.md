## 1. 核心结论

智能软件工厂当前产品形态，应定位为 **AI 原生应用平台中的生成层 / 建层产品化工作台**。

它不是传统项目管理系统，也不是普通员工状态看板；它的核心价值是：把业务输入和语义底座转化为可执行、可追踪、可验收的应用生成流程，并通过数字员工、Skill、Runtime 和治理闭环持续推进应用建模、代码生成、验证、发布与演进。

一句话定位：

```text
智能软件工厂 = AI 驱动应用生成的生产调度台。
```

主链路为：

```text
业务输入 / 业务本体
  → 语义理解 / 本体语义底座
    → 生成层动态工作流
      → Plan / Stage / WorkItem / Task / Step
        → 数字员工 + Skill + Runtime 执行
          → 应用蓝图 / 页面 / 服务 / 配置 / 测试 / 发布包
            → 反馈 / 治理 / 持续演进
```

## 2. 五层能力体系映射

用户提供的“五层能力体系”中，智能软件工厂与各层的关系如下：

| 层级 | 架构含义 | 软件工厂中的落点 | 说明 |
|---|---|---|---|
| 01 输入层 · 源 | 知识资产与业务输入，是 AI 理解业务的源头 | Project 输入、业务目标、用户需求、规范、数据接口、业务流程、指标口径、案例模板 | 软件工厂不直接替代源系统，但要能接收这些输入形成项目上下文。 |
| 02 语义层 · 懂 | 业务本体，是 AI 的共同语言 | 概念、关系、规则、指标、流程、场景、ProjectContextSnapshot、WorkItem 语义约束 | 生成层必须引用语义底座，避免只按自然语言猜测实现。 |
| 03 生成层 · 建 | 应用建模与代码生成，是落地的蓝图 | **智能软件工厂核心层**：Plan、Stage、WorkItem、Task、Step、AgentTeam、Skill、生成产物 | 当前产品主战场，应重点表达“AI 如何生成应用”。 |
| 04 执行层 · 行 | 业务能力运行与智能体协同 | ORCH、task-runner、task-batch-runner、RuntimeGateway、RuntimeSandbox、OpenCode RuntimeNode、AgentActivity | 执行层是生成层的动力与回写来源，不应抢占用户主入口。 |
| 05 治理层 · 治 | 治理运营、质量、合规、生命周期 | DecisionPacket、QA Report、Review、Artifact Evidence、Version、Audit、Risk、Cost/Resource | 治理层保障生成过程可靠、可控、可持续演进。 |

其中，**当前软件工厂页面和文档设计应优先围绕 03 生成层展开**，同时把 01/02 作为输入和语义依据，把 04/05 作为执行与治理支撑。

## 3. 生成层的内部构成

根据“AI 驱动的应用建模与生成”架构图，生成层可拆成六个核心区域。

### 3.1 生成输入

输入包括：

```text
业务本体：概念、关系、规则、指标、流程、场景
业务目标：目标、关键场景、成功标准
规则约束：策略、合规、边界、质量门禁
场景模板：行业模板、最佳实践、应用样板
数据与接口：数据源、API、服务能力输入
```

软件工厂中的对应表达：

- Project 创建 / 项目上下文；
- Plan / Stage 的目标与成功标准；
- WorkItem 的业务范围、验收标准、规则约束；
- Skill 与数据接口调用关系；
- Mock 数据、接口契约和原型参考。

### 3.2 AI 驱动动态工作流调度

生成层的调度骨架是：

```text
Plan → Stage → WorkItem → Task → Step
```

含义：

- `Plan`：应用生成计划和总体目标；
- `Stage`：计划下的阶段目标；
- `WorkItem`：可交付、可验收的工作项 / 任务项；
- `Task`：ORCH 最小派工单元；
- `Step`：task-runner 内部执行节点。

该链路必须支持：

```text
自动拆分 → 动态编排 → 执行推进 → 状态回写 → 反馈闭环
```

### 3.3 业务本体语义底座

生成层不能只围绕任务列表工作，还必须引用语义底座：

```text
概念 / 关系 / 规则 / 指标 / 流程 / 场景
```

软件工厂后续页面和文档中，WorkItem / Task 应尽量能说明：

- 它对应哪个业务概念或对象；
- 涉及哪些规则和指标；
- 修改了哪段流程或场景；
- 生成了哪些页面、服务、配置或测试；
- 验收时如何回到业务目标和规则约束。

### 3.4 业务建模智能体

业务建模智能体负责把业务输入转成生成层可执行的模型和任务，包括：

- 本体解析；
- AI 业务建模；
- 人机建模界面；
- 建模工具调用；
- 计划、阶段、工作项拆解；
- 风险和规则边界识别。

在当前岗位/员工设计中，它主要对应：

```text
协同规划岗 / 组长 / 产品规划类数字员工
```

### 3.5 AI 编程智能体

AI 编程智能体负责把模型和任务落成代码、页面、服务、配置和测试，包括：

- 代码生成；
- 接口与服务生成；
- 测试与修复；
- 发布准备；
- 文档与脚本生成。

在当前岗位/员工设计中，它主要对应：

```text
实现验证岗 / 实现类数字员工 / 测试修复类数字员工
```

### 3.6 模型与工具支撑

生成层需要模型与工具支撑：

```text
模型模板 / 组件库 / 工具链 / 发布配置 / 版本管理
```

在当前产品中对应：

- Skill 目录与调用关系；
- RuntimeGateway / RuntimeSandbox / OpenCode RuntimeNode；
- 组件、模板、脚手架、校验脚本；
- 版本控制、变更追踪、回滚和发布准备。

## 4. 生成输出映射

生成层最终不只输出“任务完成”，而应输出应用生成相关产物。

| 架构图中的生成输出 | 软件工厂中的表达 |
|---|---|
| 应用蓝图 | Plan / Stage / WorkItem / 架构设计 / 原型设计 |
| 智能体配置 | AgentTeam、岗位、员工、Skill、Runtime 绑定、权限配置 |
| 业务 Skill 调用关系 | Skill 目录、调用拓扑、任务所需能力清单 |
| Web / PC 应用 | 页面、组件、前端 feature、交互流程 |
| 移动端应用 | 移动端页面、小程序或移动适配任务 |
| AI 助手 | 面向业务用户的对话式能力、Agent 配置和工具入口 |
| 运行配置 | 环境、权限、路由、发布配置、诊断入口 |

首页和项目页后续应逐步从“任务状态”扩展为“生成产物状态”：用户能看到当前 WorkItem 正在生成什么、已经生成什么、哪些产物待验证或待发布。

## 5. 对现有产品模块的映射

| 当前模块 | 在生成层中的定位 | 调整方向 |
|---|---|---|
| 首页 / 总览 | 生成态驾驶舱 | 展示活跃应用生成流程、WorkItem、TaskBatch、员工活动、决策与风险。 |
| 项目 Projects | 应用生成对象 | 承载业务输入、计划、阶段、工作项、共享事实源和生成产物。 |
| 团队 Teams | 生成协同单元 | 展示 Team 如何围绕 Project / WorkItem 执行生成任务。 |
| 员工 Pool | 生成能力载体 | 员工状态必须绑定到 Task / Step / Skill / Runtime 活动。 |
| 岗位 Roles | 生成角色模板 | 区分业务建模、协同规划、实现验证、运行治理等能力。 |
| 技能 Skills | 生成工具与能力目录 | 管理业务 Skill、开发 Skill、验证 Skill、运行 Skill 的调用关系。 |
| 待决策 Decisions | 人机协同暂停点 | 处理规则确认、范围变更、质量风险、发布取舍等关键决策。 |
| 运行网关 RuntimeGateway | 执行基础设施 | 作为生成执行支撑和诊断下钻，不作为主业务入口。 |

## 6. 对总览页的设计要求

总览页后续应体现“生成层正在发生什么”，核心问题不是“有多少人在线”，而是：

```text
当前哪些业务应用正在被 AI 生成？
它们分别处于哪个 Plan / Stage / WorkItem？
当前 TaskBatch 走到第几个 Task？
当前 Step 是什么？
哪些员工 / 智能体正在建模、编码、验证、协同或组长把关？
哪些规则、风险或决策阻塞了生成推进？
已经生成了哪些应用产物，下一步是什么？
```

因此，总览页卡片、动态事件和详情抽屉应统一围绕：

```text
业务目标 → Plan → Stage → WorkItem → TaskBatch → Task → Step → 员工活动 → 生成产物 → 验收 / 决策 / 反馈
```

这也是 `docs/specs/SDD-OVERVIEW-DYNAMIC-WORKFLOW-UI-v0.6.33.md` 的上位设计依据。

## 7. 设计边界

### 7.1 必须坚持

- 以应用生成流程为主线，不以聊天或资源监控为主线；
- 以 Plan / Stage / WorkItem / Task / Step 驱动页面；
- 员工、Skill、Runtime 都要落到具体生成活动；
- DecisionPacket、QA、Review、Evidence 必须形成治理闭环；
- 运行基础设施作为支撑与下钻，不喧宾夺主。

### 7.2 暂不扩大

- 不在当前阶段实现完整低代码建模平台；
- 不把本体编辑器作为首页主入口；
- 不把 RuntimeGateway 页面做成 Web IDE；
- 不一次性重构所有页面；
- 不把生成层、执行层、治理层混成同一个复杂页面。

---

## 8. 后续落地优先级

1. **总览页生成态表达增强**：先在 overview 中落地 Plan / Stage / WorkItem / Task / Step 与员工活动绑定。
2. **项目页共享事实源增强**：让 Project 能展示业务输入、语义依据、生成产物和执行账本。
3. **团队页生成协同增强**：展示 Team 如何围绕 WorkItem 执行 TaskBatch。
4. **员工页活动绑定增强**：员工状态绑定 Task / Step / Skill / Runtime。
5. **待决策页生成闭环增强**：DecisionPacket 明确来自哪个 WorkItem / Task / Step，处理后如何恢复执行。
6. **技能页调用关系增强**：展示业务 Skill、开发 Skill、验证 Skill、运行 Skill 的调用拓扑。
