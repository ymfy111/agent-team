## 0. 版本升格说明

本版不是推翻 v0.6.33，而是把产品主体从**智能软件工厂**升格为 **DEOS 数字员工操作系统**，并补齐此前缺失的应用侧需求，同时把 2F「运行支撑」显式定义为数字员工运行平台。

```text
产品主体：智能软件工厂  →  数字员工操作系统（DEOS）
原智能软件工厂  =  DEOS 的构建侧（2F 构建型数字员工 + 运行 / 管理底座）
本版核心增量    =  应用型数字员工（应用侧）+ 数字员工运行平台显式化
```

三条升格要点：

1. **范围升格**：DEOS 统管「建 / 跑 / 管 / 运营」四件事；原智能软件工厂只覆盖「建」（构建侧）。
2. **名称退场**：`agent-team` / 「智能软件工厂」不再作为产品名，统一称 DEOS 及其分层组件。
3. **术语净化**：产品口径统一用「数字员工」，对外不出现「智能体 / Agent」（见 §9）。

v0.6.33 已稳定的构建侧需求（三岗、任务单闭环、结构化 Markdown）在本版**保留并归位为构建侧**，细节沿用既有文档，不重复展开。

## 1. 产品定位

DEOS 是一套以**数字员工**为运行主体的操作系统：让**两类数字员工**在**业务本体**之上，把业务**建起来**、**跑起来**。

```text
建    构建型数字员工把业务需求转成可运行的应用与能力
跑    应用型数字员工持续执行业务任务
管    管理平台对数字员工做编制、授权、配置
运营  运营平台保障数字员工的运行效能与成本
```

四层架构（详见架构总纲 `SDD-DEOS-ARCHITECTURE-v0.7.md`）：

```text
4F 用户终端     构建侧(开发) | 应用侧(业务·运营)
3F 系统层       管理平台 | 运营平台 | 业务系统
2F 运行层       构建型DE   能力库   应用型DE   + 动态工作流引擎 / 运行支撑
1F 本体层       业务本体 · Ontology
                安全合规 · 全栈贯穿
```

> 与 v0.6.33 的关系：原「AI 原生应用平台生成层 / 建层工作台」是 DEOS 的**构建侧（2F 构建型）**，并非 DEOS 全貌。

## 2. 两类数字员工总览

DEOS 的核心命题：**两类数字员工，一类把业务建起来，一类把业务跑起来。**

| 维度 | 构建型数字员工（构建侧）| 应用型数字员工（应用侧）|
|---|---|---|
| 定位 | 人机共建 · 开发交付 | 持续运行 · 协同执行 |
| 周期 | 慢循环 · 版本制 | 快循环 · 任务制 |
| 产出 | 应用 + 能力 | 业务执行结果 |
| 现状 | 已实现（承接 v0.6.33）| **核心增量（本版新立需求）** |
| 循环 | 需求与设计→计划拆解→建模与编码→验收发布 | 任务唤醒→任务执行→人机协同→执行反馈 |

两类员工共享 **2F 数字员工运行平台**（§5）、**能力库**与**业务本体**，构建型沉淀、应用型调用并回流，形成「越跑越准」的闭环。

## 3. 构建侧产品需求（承接 v0.6.33）

构建侧即原智能软件工厂，是面向 AI 数字员工团队的软件研发协作系统。本版保留其需求，仅做术语净化与归位。

### 3.1 构建型角色

| 岗位 | 职责 | 归类 |
|---|---|---|
| 协同规划岗 | 理解目标、生成计划、拆解与维护任务清单、接收反馈、决定下一步 | 构建型组长（原主导数字员工）|
| 实现验证岗 | 读取任务单、执行实现 / 修改 / 验证、回写执行反馈 | 构建型执行数字员工 |
| 交付审查岗 | 审查产物、形成通过 / 返工 / 待决策结论、回写审查记录 | 构建型质量门禁 |
| 用户 | 只在关键节点介入：需求边界、业务取舍、技术方向、高风险确认、验收 | 人 |

### 3.2 构建侧工作方式

第一阶段沿用「**协同规划岗驱动任务清单**」模式（非完整状态机），最小闭环：

```text
用户目标 → 协同规划岗生成计划 → 拆解任务清单 → 系统持久化
  → 按任务单指派构建型数字员工执行 → 实现验证岗执行并反馈
  → 系统记录任务事件 → 协同规划岗更新下一步
  → 交付审查岗审查 → 必要时进入待决策工作台
```

### 3.3 构建侧既有需求（沿用 v0.6.33）

以下需求维持有效，细节历史参考见 `docs/archive/agent-team-v0.6.33/specs/PRD-v0.6.33.md` 对应章节：

- 结构化 Markdown 任务文档（任务单最小结构、程序读写边界）——v0.6.33 §4。
- 原型模块与产品口径映射——v0.6.33 §5。
- 结构化协作要求（Plan / Task / Review / Decision Markdown）——v0.6.33 §8。
- 界面稳定、机制演进原则；岗位产出表达；Mock 数据真实性——v0.6.33 §9。

## 4. 应用侧产品需求（新增 · 核心增量）

应用型数字员工是 DEOS v0.7 的核心增量：常驻运行、任务制，调用能力把业务跑起来。本版立其产品需求骨架，详细运行模型见 `SDD-APPLICATION-DE-v0.7.md`。

### 4.1 应用型角色与职责

```text
监听触发（业务事件 / 定时 / 人工指派 / 上游任务）
  → 调用能力库执行业务动作
    → 关键节点人机协同（确认 / 审批 / 干预 / 接管）
      → 回写执行结果，运行数据回流业务本体
```

### 4.2 触发与运行

| 需求 | 说明 |
|---|---|
| 任务唤醒 | 支持事件触发、定时触发、人工指派、上游任务触发四种唤醒方式 |
| 任务执行 | 按业务本体规则调用能力库（技能 / 工具 / 接口 / 知识库 / 大模型）执行 |
| 任务制粒度 | 单圈短周期、可并发，区别于构建侧的版本制长周期 |
| 执行反馈 | 产出执行结果与业务指标，回写任务并回流 1F 业务本体 |

### 4.3 人机协同节点

应用型数字员工自主执行 + 人在回路，关键点必须可由人介入：

```text
确认  执行前对高影响动作确认
审批  对越权 / 高风险动作走审批
干预  运行中暂停 / 调整 / 纠偏
接管  异常时转人工接管
```

### 4.4 与业务系统协同

- 应用型数字员工与业务系统（`ERP` / `MES` / `设备管理` / `安全生产` 等）人机共用、读写协同。
- 集成模式需支持多形态（API 对接 / 消息总线 / RPA 代操，按系统能力选择）。
- 数据主权、操作权限边界由安全合规层（§见架构总纲 §7）约束。

### 4.5 应用侧终端（4F 应用侧）

| 终端 | 使用者 | 内容 |
|---|---|---|
| 业务数据看板 | 业务 | 业务运行态、产出、异常 |
| 运行监控仪表盘 | 运营 | 数字员工运行状态、效能、成本 |
| 待办 / 审批台 | 业务 / 运营 | 人机协同节点的确认、审批、干预入口 |

## 5. 数字员工运行平台需求（2F 运行支撑）

数字员工运行平台对应架构图 2F 的**运行支撑**带：`动态工作流引擎` + `任务调度 / 任务编排` + `服务注册 / 服务发现`，是承载两类数字员工调度运转的底座。原 agent-team 已实现其框架（仅构建侧），本版需扩展支持应用型任务制运行。

> 范围界定：运行平台 = 运行支撑，**不含能力库**。能力库是 2F 内与运行平台并列的共享组件（见 §5.5）。

### 5.1 动态工作流引擎（流程中枢 · 调度大脑）

```text
依据业务本体编排任务、驱动数字员工运转
同时承载：构建侧版本制流程（Plan/Stage/WorkItem/Task/Step）
          应用侧任务制快循环（AppTask/Session/Step）
```

### 5.2 任务调度 · 任务编排（任务侧）

```text
任务调度：把任务排期、分配运行
任务编排：把任务组装成可执行流程
```

### 5.3 服务注册 · 服务发现（资源侧）

```text
服务注册：注册可用的数字员工实例与能力 / 服务
服务发现：运行时发现并路由到可调用的能力 / 服务
```

### 5.4 数字员工运行管理

```text
实例注册 / 心跳 / 路由 / 绑定 / 生命周期   —— RuntimeGateway 能力
多数字员工编排                              —— TeamOrchestrator 能力
平台后台只联系 Gateway，由 Gateway 承载本地执行
运行态可观测：运行状态、执行账本、调用记录，供 3F 运营平台（§6.2）消费
```

### 5.5 关联：能力库（2F 共享组件，与运行平台并列）

能力库（`技能 / 工具 / 接口 / 知识库 / 大模型`）**不属于运行平台**，是 2F 内与之并列的共享组件：构建型沉淀入库，运行平台经服务发现对接，供两类数字员工调用。

### 5.6 现状与增量

| 组件 | 现状 | 增量 |
|---|---|---|
| 动态工作流引擎 | ✓ 已实现（TaskFlow / Task Runner / ORCH）| 扩展应用型任务制运行（App Task Runner）|
| 任务调度 / 编排 | ✓ | 面向应用型触发与并发扩展 |
| 服务注册 / 发现 | ✓ RuntimeGateway | 覆盖应用型实例常驻运行 |
| 运行管理 | ✓ Gateway / 编排 | 应用型实例生命周期管理 |

## 6. 系统平台需求（3F）

### 6.1 数字员工管理平台（集中管理 · 权限配置）

```text
权限 / 岗位 / 技能 / 团队 / 配置管理
覆盖两类数字员工的编制治理（现状偏构建型，需扩到应用型）
```

### 6.2 数字员工运营平台（效能保障 · 成本优化）

```text
运行监控 / 运营看板 / 性能告警 / 成本 / 调优
数据来源于 2F 运行平台可观测（§5.4）
现状部分实现，需补齐应用型数字员工的运营
```

### 6.3 业务系统（业务承载 · 人机共用）

```text
承载实际业务的企业应用系统群，人与应用型数字员工共同使用
本版需求：建立应用型数字员工与业务系统的对接能力
```

> 3F 三平台产品化定义与现状参见架构总纲 §5。

## 7. 用户终端需求（4F）

| 侧 | 角色 | 终端 | 现状 |
|---|---|---|---|
| 构建侧 | 开发 | 构建工作台（计划 / 任务 / 团队 / 决策视图）| 已实现 |
| 应用侧 | 业务 / 运营 | 业务看板 / 运行监控 / 待办审批 | 增量待建（§4.5）|

界面原则延续 v0.6.33「**界面稳定，机制演进**」：用户心智围绕「业务是否在推进、数字员工在做什么、要不要人介入」，不暴露底层状态机 / 运行时细节。

---

## 8. 安全合规需求（全栈贯穿）

```text
安全防护 / 身份认证 / 密码管理 / 性能监控 / 合规审计
```

应用型数字员工引入后的新增关注点（需在应用侧子设计落实）：

- 数字员工操作业务系统的**权限边界**；
- 数字员工代人执行时的**授权 / 审批模型**；
- 数字员工业务决策的**可追溯性**。

## 9. 术语净化口径

产品文档统一口径，对外零「智能体 / Agent」：

| 旧表述 | 新表述（产品口径）|

| 智能体 | 数字员工 |

## 11. 验收口径

### 11.1 构建侧（承接 v0.6.33）

后续原型 / 实现应能回答：组长如何生成计划、任务清单在哪、任务分派给谁、执行如何反馈、状态如何变化、审查结论如何回写、用户何时介入、项目健康如何汇总。

### 11.2 运行平台（2F）

```text
能说明两类数字员工如何注册、调度、绑定运行时
能说明动态工作流引擎如何同时承载版本制与任务制
能说明运行平台如何通过服务发现对接能力库
能说明运行态数据如何供运营平台消费
```

### 11.3 应用侧（新增）

应用型数字员工产品需求成立的判据：

```text
能说明应用型数字员工如何被唤醒（四种触发）
能说明一个业务任务的执行 → 人机协同 → 反馈完整链路
能说明与业务系统的集成模式与权限边界
能说明运行数据如何回流业务本体
能在应用侧终端看到业务运行态与待办 / 审批
```
