## 1. 背景

用户基于当前首页截图进一步明确：**智能软件工厂不是静态员工看板，也不是单纯资源监控页，而是以 AI 动态工作流驱动的软件研发协作平台**。

首页需要让用户一眼看清：

1. 当前有哪些计划 / 阶段 / 任务项正在推进；
2. 每个任务项下当前批次、任务、步骤走到哪里；
3. 哪些数字员工正在围绕这些活动执行、协作、验证或等待；
4. 哪些任务项因为待决策、异常或验证门禁需要用户介入；
5. ORCH / task-runner / task-batch-runner 的动态调度结果如何反映到页面。

---

## 2. 核心产品口径

### 2.1 工作驱动层级

后续总览页表达应围绕以下层级组织：

```text
计划 Plan
  → 阶段 Stage
    → 任务项 / 工作项 WorkItem
      → 任务 Task
        → 步骤 Step / Node
```

说明：

- 用户口径中“任务项”与既有文档中的 `WorkItem / 工作项` 指同一层级；后续页面文案可根据语境使用“任务项”或“工作项”，但数据模型统一映射到 `WorkItem`。
- `TaskBatch` 是同一 WorkItem 下多个 Task 的连续执行批次，用于表达 `0/4`、`1/4` 这类批次进度。
- `task-runner` 执行单个 Task 的内部步骤；`task-batch-runner` 串联同一 WorkItem 下的 Task 队列。

### 2.2 员工活动必须落到工作流活动

数字员工不应只以“人员卡片 / 在线状态 / 忙闲状态”出现。每个员工状态都应绑定到具体活动：

- 绑定到哪个 Team；
- 服务哪个 Project；
- 正在推进哪个 Plan / Stage / WorkItem；
- 当前负责哪个 Task 或 Step；
- 当前角色是执行、协同、验证、组长把关还是等待；
- 当前状态是空闲、忙碌、离线、待确认、被阻塞或已完成。

员工卡片的价值不是展示头像，而是帮助用户判断：**谁正在做什么、下一步该谁处理、是否需要我介入**。

## 3. 截图需求提炼

### 3.1 首页总览结构

截图中的首页包含四类信息区：

1. **顶部全局指标卡**
   - 协作团队数量；
   - 可调度员工数量；
   - 进行中任务项 / 工作项数量；
   - 待处理决策数量。

2. **协作全景 / Team WorkItem 卡片区**
   - 按团队展示当前正在交付的任务项；
   - 每张卡片包含团队名称、项目 / 任务项名称、阶段标签、组长 / 管理者、当前批次进度、当前任务摘要、执行员工活动状态；
   - `0/4`、`1/4` 这类数字应表达“当前批次任务完成进度”，不是泛化的“任务完成”。

3. **团队动态 / 工作项事件流**
   - 右侧事件流展示最近发生或需要关注的工作项动态；
   - 每条动态应说明来源团队 / 项目、当前交付任务项、状态、进度、当前任务、待决策或阻塞信息；
   - 用户可以从这里快速进入详情或处理决策。

4. **工作项详情抽屉**
   - 点击工作项或动态后展开右侧详情抽屉；
   - 抽屉应按任务项 / 工作项维度汇总当前状态，而不是只展示一条消息。

### 3.2 工作项详情抽屉内容

截图中的详情抽屉应沉淀为后续实现标准结构：

```text
工作项标题
  状态摘要：进行中 / 待决策 / 阻塞 / 已完成
  当前风险或待处理提示

基础信息
  计划 / 阶段
  当前批次
  预计完成
  实际运行

任务列表
  Task 序号
  Task 名称
  TaskId
  Task 状态：执行中 / 待决策 / 草稿 / 已完成 / 阻塞

执行与验收
  执行人 / 协同人 / 验证人 / 组长把关
  当前 Step / Node
  验证或验收状态

停止策略
  任务失败
  等待决策
  运行异常
  验证不通过
  质量不收敛
```

### 3.3 动态性的表达要求

页面要体现“动态工作流”，不是静态项目列表：

- 状态应来自 Task / TaskBatch / DecisionPacket / AgentActivity 的变化；
- Team 卡片里的当前任务、批次进度、员工活动会随调度推进变化；
- 右侧团队动态是最近事件和需要关注事项，不是固定公告；
- 抽屉用于把动态事件还原到完整的工作项上下文。

## 4. 首页信息架构建议

### 4.1 顶部指标卡

建议保留 4 张指标卡，但语义统一为工作流驱动指标：

| 指标 | 推荐含义 | 可点击下钻 |
|---|---|---|
| 协作团队 | 当前有活跃任务项的 Team 数 | Team 运行视图 |
| 可调度员工 | 可参与 Task / Step 的员工数 | 员工运行绑定视图 |
| 进行中任务项 | 当前 running / blocked / waiting-decision 的 WorkItem 数 | WorkItem 列表 |
| 待处理决策 | 需要用户或组长处理的 DecisionPacket 数 | Decisions 页面 |

### 4.2 Team 工作项卡片

每张 Team 卡片应包含：

| 区块 | 内容 |
|---|---|
| 顶部 | Team 名称、项目 / 任务项名称、当前阶段标签、详情入口 |
| 负责人 | 组长 / 协同规划岗，职责为计划跟踪、风险协调、最终验收把关 |
| 当前批次 | TaskBatch 状态、`x/y` 批次进度、当前 Task 摘要 |
| 员工活动 | 员工头像、岗位编号、当前 Task / Step、忙闲/离线状态 |
| 风险提示 | 待决策、验证不通过、运行异常、阻塞原因 |

注意：不要把“审查岗 / 收尾岗”作为固定岗位突出；最终验收和收尾把关由组长 / 协同规划岗承担，验证能力可以由实现验证类员工承担。

### 4.3 团队动态事件流

右侧事件流推荐字段：

```text
来源团队 / 项目
事件标题：<任务项> 当前交付工作项
状态：进行中 / 待决策 / 阻塞 / 已完成
批次进度：x/y
当前 Task
待决策 / 风险摘要
操作：查看 / 处理
```

排序原则：

1. 待用户处理 / 高风险优先；
2. 最近发生事件优先；
3. 进行中但正常推进的事件次之；
4. 已完成事件默认折叠或弱化。

### 4.4 工作项详情抽屉

抽屉的目标是回答用户四个问题：

1. 这个任务项属于哪个计划和阶段？
2. 当前正在执行哪一批任务，走到第几个？
3. 哪些员工正在执行 / 验证 / 等待？
4. 为什么停住或为什么需要我处理？

抽屉不应过度展示底层 Runtime / Gateway 技术细节；这些信息可作为“运行证据 / 诊断入口”下钻。

## 5. 数据对象映射

| 页面概念 | 数据对象 | 说明 |
|---|---|---|
| 计划 | `Plan` | 顶层目标和路线图 |
| 阶段 | `Stage` | 计划下的目标区间 |
| 任务项 / 工作项 | `WorkItem` | 可验收的交付单元 |
| 当前批次 | `TaskBatch` | 同一 WorkItem 下多个 Task 的顺序执行批次 |
| 任务 | `Task` | ORCH 最小派工单元 |
| 步骤 | `Step` / `Node` | `task-runner` 内部执行节点 |
| 员工活动 | `AgentActivity` / `EmployeeAssignment` | 员工与 Task / Step 的绑定状态 |
| 待决策 | `DecisionPacket` | 用户或组长必须处理的暂停点 |
| 运行事件 | `TaskEvent` / `OrchEvent` | 团队动态事件流来源 |

## 6. 视觉与交互约束

1. **保留现有首页整体风格**：只做业务结构增强，不做大幅视觉重构。
2. **进度必须紧凑完整显示**：`0/4`、`1/4` 这类批次进度不能被截断，也不能写成“任务完成”造成误解。
3. **卡片优先表达结论**：先展示当前状态、风险、下一步行动，再展示底层字段。
4. **抽屉用于上下文补全**：主卡片保持简洁，复杂任务列表、执行与验收、停止策略放入抽屉。
5. **动态事件可操作**：待决策或阻塞事件必须提供“处理 / 查看”入口。
6. **避免过拟合截图细节**：截图中的比例、间距、部分文案可调整；必须保留的是信息层级、业务逻辑、字段优先级、状态结论和操作入口。

## 7. 后续实现验收标准

后续修改 `overview/page.js` 时至少满足：

- 首页能明确表达 `Plan → Stage → WorkItem → Task → Step` 的动态工作流层级；
- Team 卡片中的员工状态都绑定到具体任务或步骤；
- 任务项卡片展示当前批次进度，`x/y` 含义清晰且不被截断；
- 右侧团队动态能反映待决策、阻塞和当前交付工作项；
- 点击任务项或动态能打开工作项详情抽屉；
- 抽屉包含基础信息、任务列表、执行与验收、停止策略；
- 页面仍保持现有设计风格，不做破坏性重构；
- Playwright 截图验证通过，并输出修改前后对比截图。
