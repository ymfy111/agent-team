## 1. 总体定位与设计理念

### 1.1 DEOS 是什么

DEOS 是一套以**数字员工**为运行主体的操作系统。它不是单一应用，而是统管以下四件事的平台底座：

- **建**：构建型数字员工把业务需求转成可运行的应用与能力。
- **跑**：应用型数字员工持续执行业务任务。
- **管**：管理平台对数字员工做编制、授权、配置。
- **运营**：运营平台保障数字员工的运行效能与成本。

四件事统一运行在 **1F 业务本体（Ontology）** 这一共享语义底座之上。

### 1.2 核心命题

DEOS 的核心命题只有一句：**两类数字员工，一类把业务建起来，一类把业务跑起来。**

- **构建型数字员工**：理解业务、建模、写代码，产出「应用 + 能力」。
- **应用型数字员工**：调用能力、执行任务、与人协同，把业务跑起来。

两类员工不是孤立的，它们通过**业务本体**与**能力库**形成闭环：

```text
构建型数字员工 ──产出能力 / 沉淀语义──▶ 能力库 / 业务本体
                                          │
业务本体 / 能力库 ──供给语义 / 可调用能力──▶ 应用型数字员工
                                          │
应用型数字员工 ──运行反馈 / 数据回流──────▶ 业务本体
```

业务本体是「越跑越准的业务大脑」：构建型往里沉淀，应用型从里取用并回流，双向闭环。

### 1.3 设计原则

1. **业务本体为中枢**：语义、关系、规则、指标、数据、流程统一沉淀在 1F，所有层共享同一套业务语义，避免各模块各说各话。
2. **能力沉淀复用**：构建型产出的技能/工具/接口/知识统一入**能力库**，两类数字员工按需调用，不重复造。
3. **人机协同**：关键决策点由人确认、审批、干预；数字员工自主执行 + 人在回路。
4. **跨层堆叠、低耦合**：四层自下而上堆叠，层间通过明确接口调用，不做跨层直连耦合（架构图上体现为「不画跨层箭头」）。
5. **对外零智能体口径**：对外统一称「数字员工」，不使用「智能体 / Agent」作为产品词（技术实现内部技术名词不受此约束，见附录 A）。

### 1.4 从 agent-team 到 DEOS（升格说明）

原 `agent-team`（智能软件工厂）已经实现了一套**数字员工运行底座 + 管理平台 + 部分运营平台**，但有一个明确边界：**其中的数字员工只覆盖构建侧（构建型），尚未纳入应用侧（应用型）**。

因此 DEOS 的升格不是推倒重来，而是：

- **保留**：既有的运行层底座（动态工作流引擎、运行网关、能力调用）、管理平台、部分运营平台——这些本就是 DEOS 的 2F / 3F 组成。
- **补齐**：在同一套底座上接入**应用型数字员工**，并连带补**应用侧用户终端、业务系统集成、运营平台的应用侧部分**。

```text
原 agent-team 实现  ≈  DEOS 的【构建侧 + 运行 / 管理底座】
DEOS 升格核心增量    =  应用型数字员工（应用侧）接入同一套底座
```

自 v0.7.0 起，`agent-team` 不再作为独立产品名出现，统一以 DEOS 及其分层组件称谓。

## 2. 总体架构：四层模型总览

### 2.1 四层总图

DEOS 自上而下分四层，安全合规全栈贯穿：

```text
┌─────────────────────────────────────────────────┐
│ 4F 用户终端     构建侧(开发) │ 应用侧(业务·运营)     │
├─────────────────────────────────────────────────┤
│ 3F 系统层       管理平台 │ 运营平台 │ 业务系统        │
├─────────────────────────────────────────────────┤
│ 2F 运行层       构建型DE    能力库    应用型DE        │
│                └──── 动态工作流引擎 / 运行支撑 ────┘  │
├─────────────────────────────────────────────────┤
│ 1F 本体层            业务本体 · Ontology             │
└─────────────────────────────────────────────────┘
   ▏安全合规 · 全栈贯穿（横切 4F–1F，底部贯通）▕
```

### 2.2 逐层定位

| 层 | 名称 | 一句话定位 |
|---|---|---|
| 4F | 用户终端 | 人通过构建侧 / 应用侧终端与数字员工协同 |
| 3F | 系统层 | 管数字员工（管理）、保效能（运营）、接业务（业务系统）|
| 2F | 运行层 | 两类数字员工的运行底座 + 能力库 + 调度引擎 |
| 1F | 本体层 | 全局业务语义底座，越跑越准的业务大脑 |
| — | 安全合规 | 横切四层的安全、认证、审计、监控 |

### 2.3 层间关系与设计哲学

- **堆叠依赖**：上层依赖下层供给的能力，1F 本体为所有层供给语义，2F 运行层为 3F / 4F 提供运行实体。
- **调用而非耦合**：层间通过明确接口交互；架构图刻意不画跨层箭头，强调「靠分层堆叠表达依赖，而非用一堆穿层连线表达耦合」。
- **中央主轴**：`能力库 → 动态工作流引擎 → 业务本体` 在 2F→1F 方向垂直对齐，是 DEOS 的运行主轴——能力被引擎调度、引擎依据本体决策。

### 2.4 现状 / 增量总览

全文每层均按此口径标注：

- **现状（既有实现）**：构建侧那条线 + 运行 / 管理底座已落地。
- **增量（DEOS v0.7 待补）**：应用侧（应用型数字员工）及其连带的终端、业务系统集成、运营应用侧。

## 3. 1F 业务本体层（Ontology）

### 3.1 定位

业务本体是 DEOS 的**语义底座**与**业务大脑**。它为上层所有数字员工提供统一的业务语言：构建型据此建模，应用型据此执行，管理 / 运营据此度量。

### 3.2 组成

| 要素 | 含义 |
|---|---|
| 统一语义 | 业务概念的统一定义，消除同义不同名 |
| 关系 | 概念之间的关联与依赖 |
| 规则 | 业务约束、校验、决策规则 |
| 指标 | 可度量的业务度量项 |
| 数据 | 业务数据的结构与归属 |
| 流程 | 业务流程的定义（区别于 2F 的运行时工作流）|

> 注：1F「流程」是**业务流程的本体定义**（静态、概念级）；2F 动态工作流引擎是**运行时编排**（动态、执行级）。两者同名不同层，前者是后者的依据。

### 3.3 双向闭环

```text
构建型数字员工 ──沉淀(新建 / 更新语义·规则)──▶ 业务本体
业务本体 ──供给(语义·规则·指标)──▶ 构建型 / 应用型数字员工
应用型数字员工 ──回流(运行数据·指标反馈)──▶ 业务本体
```

构建时沉淀、运行时回流，业务本体随业务运转持续精化，这是「越跑越准」的机制来源。

### 3.4 现状与映射

- **现状**：业务本体已作为生成层的语义底座存在，为构建型数字员工的建模 / 生成提供约束与共同语言（历史参考见 `docs/archive/agent-team-v0.6.33/specs/SDD-GENERATION-LAYER-ARCHITECTURE-v0.6.33.md`）。
- **增量**：升格为**全局双向闭环底座**——打通应用型数字员工的运行数据回流路径，使本体不仅服务构建，也吸收运行反馈。

## 4. 2F 运行层（核心）

2F 是 DEOS 的运行核心，承载两类数字员工、能力库、动态工作流引擎与运行支撑。

### 4.1 两类数字员工

**构建型数字员工**——定位「人机共建 · 开发交付」，是一支 AI 软件研发团队，把业务建出来：

```text
①需求与设计 → ②计划拆解 → ③建模与编码 → ④验收发布 ↻
```

- 单圈周期长、版本制，产出「应用 + 能力」。
- 对应既有实现：智能软件工厂主线，`Plan / Stage / WorkItem / Task / Step` 任务流驱动多数字员工协同（`SDD-TASKFLOW-TASKTICKET-MODEL`、`SDD-GENERATION-LAYER-ARCHITECTURE`）。

**应用型数字员工**——定位「持续运行 · 协同执行」，常驻运行，把业务跑起来：

```text
①任务唤醒 → ②任务执行 → ③人机协同 → ④执行反馈 ↻
```

- 单圈周期短、任务制，调用能力执行业务，关键点人机协同。
- **现状：尚未实现，是 DEOS v0.7 核心增量。**

两类员工的区别在于**周期与粒度**（构建＝慢循环·版本制，应用＝快循环·任务制），但都是闭环循环，都依赖能力库与业务本体。

### 4.2 能力库

能力库是构建型产出、两类员工共享调用的可复用能力池：

| 能力 | 说明 |
|---|---|
| 技能 | 可复用的业务技能单元 |
| 工具 | 工具型能力（含原 skill / MCP 归并）|
| 接口 | 对外 / 对内 API 接口 |
| 知识库 | 领域知识与检索 |
| 大模型 | 底层模型能力 |

- **沉淀**：构建型数字员工把产出的能力入库。
- **调用**：两类数字员工按需调用。
- 能力库与 1F 本体分工：能力库是**可执行能力**（做什么、用什么），本体是**业务语义**（是什么、什么规则），内容 vs 结构，互补不重叠。
- 对应既有实现：Skills 目录与调用关系（`SDD-GENERATION-LAYER-ARCHITECTURE`、`SDD-TASKFLOW-SKILL-PRODUCT-MAPPING`）。

### 4.3 动态工作流引擎与运行支撑

**动态工作流引擎**——定位「流程中枢 · 调度大脑」，是 2F 的调度核心：依据业务本体编排任务、驱动数字员工运转。运行支撑围绕引擎左右分列：

```text
任务调度 · 任务编排  ──▶  动态工作流引擎  ──▶  服务注册 · 服务发现
  (任务侧：要做什么)      (流程中枢·调度大脑)      (资源侧：用什么做)
```

- **左侧任务侧**：`任务调度`、`任务编排`——把任务排期、组装成流程。
- **右侧资源侧**：`服务注册`、`服务发现`——注册可用能力 / 服务、供运行时发现调用。
- 对应既有实现：`TaskFlow / Task Runner / ORCH`（调度编排）、`RuntimeGateway`（注册·心跳·路由·绑定）、`TeamOrchestrator`（多员工编排）。
  - 历史参考见 `docs/archive/agent-team-v0.6.33/specs/SDD-RUNTIME-GATEWAY-v0.6.33.md`、`docs/archive/agent-team-v0.6.33/specs/SDD-TEAM-ORCHESTRATOR-v0.6.33.md`、`docs/archive/agent-team-v0.6.33/specs/SDD-OVERVIEW-DYNAMIC-WORKFLOW-UI-v0.6.33.md`。

### 4.4 现状与增量

| 2F 组件 | 现状 | 增量 |
|---|---|---|
| 构建型数字员工 | ✓ 已实现 | — |
| 应用型数字员工 | ✗ 未考虑 | ★ 接入 |
| 能力库 | ✓ | 完善（面向应用型的调用治理）|
| 动态工作流引擎 / 运行支撑 | ✓ | 扩展支持应用型任务制运行 |

## 5. 3F 系统层

3F 是人用来「管数字员工、接业务」的平台层，含三块并列系统。

### 5.1 数字员工管理平台

- 定位「集中管理 · 权限配置」。
- 职能：对数字员工做编制治理——`权限`、`岗位`、`技能`、`团队`、`配置管理`。
- 使用者：管理员 / 治理者。
- 现状：已实现（偏构建型员工的管理）；增量：扩展到覆盖两类员工。

### 5.2 数字员工运营平台

- 定位「效能保障 · 成本优化」。
- 职能：运行态的 `运行监控`、`运营看板`、`性能告警`、`成本`、`调优`。
- 使用者：运营。
- 现状：部分实现；增量：补齐应用型数字员工的运营（运行监控 / 成本 / 调优）。

### 5.3 业务系统

- 定位「业务承载 · 人机共用」。
- 职能：承载实际业务的企业应用系统群（`ERP`、`MES`、`设备管理`、`安全生产` 等，按需接入），由人与应用型数字员工共同使用。
- 现状：尚未集成；增量：建立应用型数字员工与业务系统的对接。

### 5.4 三平台边界

| 平台 | 管什么 | 时态 |
|---|---|---|
| 管理平台 | 数字员工的身份与编制 | 静态建制 |
| 运营平台 | 数字员工的运行与效能 | 动态运营 |
| 业务系统 | 承载的业务本身 | 业务执行 |

管理平台管「数字员工是谁、归谁、能干啥」（编制），运营平台管「数字员工跑得好不好」（效能），两者边界清晰、互不重叠。

> 3F 三平台的产品化定义历史参考见 `docs/archive/agent-team-v0.6.33/specs/PRD-v0.6.33.md`。

## 6. 4F 用户终端

4F 是人与数字员工协同的入口，分两侧。

### 6.1 构建侧

- 角色：`开发`。
- 终端：构建工作台（代码、流程图、项目 / 团队 / 决策视图）。
- 与构建型数字员工协同，完成需求→设计→编码→交付。
- 现状：已实现（`SDD-OVERVIEW-DYNAMIC-WORKFLOW-UI`、`PRD` 工作台模块）。

### 6.2 应用侧

- 角色：`业务`、`运营`。
- 终端：业务数据看板、运行监控仪表盘。
- 与应用型数字员工协同，监督业务运行、在关键点确认 / 审批 / 干预。
- 现状：增量待补。

### 6.3 角色对应

```text
4F 构建侧(开发)   ↔  2F 构建型数字员工  ↔  3F 管理平台
4F 应用侧(业务)   ↔  2F 应用型数字员工  ↔  3F 业务系统
4F 应用侧(运营)   ↔  2F 运行支撑 / 监控  ↔  3F 运营平台
```

## 7. 安全合规（全栈贯穿）

安全合规不是单独一层，而是**横切 4F–1F 的纵向能力栏**，五项：

| 能力 | 作用 |
|---|---|
| 安全防护 | 整体安全防护 |
| 身份认证 | 用户 / 数字员工身份核验 |
| 密码管理 | 凭据与密钥管理 |
| 性能监控 | 全栈性能可观测 |
| 合规审计 | 操作审计与合规留痕 |

底部「安全合规 · 全栈贯穿」条强调：每一层的运行都在安全合规约束下进行。对应既有实现的 RBAC / SSO / 审计 / 限流等横切能力。
