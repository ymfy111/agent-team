# ADR-0009：智能软件工厂 Agent Team 编排架构决策记录

> 状态：Accepted  
> 日期：2026-05-21  
> 关联版本：v0.6.33  
> 关联原型安全基线：v0.6.33.29  
> 决策主题：主智能体任务清单驱动、主子智能体通讯、程序状态机与结构化 Markdown 的关系

---

## 1. 背景

智能软件工厂需要支持长任务、多智能体协作、计划拆解、任务执行、审查返工、用户待决策和项目健康管理。

近期讨论中，我们比较了几种思路：

```text
1. 主智能体直接与子智能体通讯，靠主智能体维护任务清单。
2. 程序状态机完全控制任务流转，主智能体只作为某个节点。
3. 多 Agent 自由沟通，类似团队群聊。
4. 分阶段演进：先主智能体任务清单驱动，后逐步程序化。
```

最终认为：**不应一开始就做完整复杂状态机，也不应把 Agent 自由聊天作为事实来源。**

---

## 2. 核心问题

需要回答：

```text
主智能体是否仍然应该负责写计划、拆任务、维护任务清单？
子智能体反馈如何被主智能体使用？
程序控制任务和进度后，Markdown 是否还合适？
状态机应该一开始就做，还是分阶段演进？
主子智能体直接通讯是否应该保留？
```

---

## 3. 方案对比

### 3.1 方案 A：主智能体驱动任务清单

流程：

```text
用户目标
→ 主智能体写计划
→ 主智能体拆解任务清单
→ 子智能体执行任务
→ 子智能体反馈结果
→ 主智能体维护任务清单变化
```

优点：

```text
实现快
灵活
适合 POC 和探索期
主智能体可以处理模糊需求
与当前项目半人工智能体协作经验匹配
```

缺点：

```text
如果没有结构化记录，任务状态容易藏在对话中
主智能体上下文变长后可能遗漏
多任务并发时容易混乱
恢复、统计、审计能力较弱
```

结论：适合作为第一阶段，但必须配合持久化任务清单和任务事件。

### 3.2 方案 B：完整程序状态机驱动

流程：

```text
程序维护任务状态
程序决定下一步流转
主智能体只在规划、重规划等节点被调用
子智能体只执行明确任务
```

优点：

```text
状态清楚
可恢复
可审计
适合多项目多团队并行
方便做权限、重试、统计和监控
```

缺点：

```text
初期设计成本高
容易过度设计
状态机太早固化会限制 Agent 灵活性
需要大量对象、状态、事件和边界设计
```

结论：适合后续产品化阶段，不适合作为第一阶段前置条件。

### 3.3 方案 C：主子智能体自由通讯

优点：

```text
自然
交互灵活
适合一次性协作和短任务
```

缺点：

```text
聊天记录不是可靠状态
任务事实不易追踪
失败难恢复
审查和待决策难制度化
用户无法快速看到项目卡在哪里
```

结论：不能作为智能工厂主流程。通讯可以保留，但必须结构化回写。

---

## 4. 最终决策

采用**分阶段演进架构**：

```text
阶段 A：Agent-led Task List
  主智能体写计划、拆任务、维护任务清单；系统持久化任务单和事件。

阶段 B：Guarded Task Flow
  系统读取结构化任务字段，增加轻量状态约束。

阶段 C：State-machine Orchestration
  程序状态机逐步接管常规流转，主智能体只在关键判断节点参与。

阶段 D：Factory Runtime Orchestration
  接入多 RuntimeHost / RuntimeNode，实现真实数字员工调度。
```

核心口径：

```text
主智能体负责想清楚。
程序负责记清楚、控流程。
子智能体负责做清楚。
交付审查岗负责验清楚。
用户负责关键取舍。
```

---

## 5. 对主子智能体通讯的决定

允许主子智能体通讯，但它不能成为事实来源。

允许：

```text
执行澄清
执行结果汇报
审查返工意见
主智能体重规划请求
```

必须回写为：

```text
TaskEvent
ExecutionResult
ReviewRecord
DecisionItem
TaskTicket 状态变化
```

禁止：

```text
主智能体口头安排任务但不创建任务单
子智能体完成工作但不回写结果
审查意见只存在聊天中
待决策事项不进入待决策工作台
多子智能体自由互相沟通决定全局流程
```

---

## 6. 对 Markdown 的决定

继续使用 Markdown，但采用**结构化 Markdown**。

原因：

```text
Markdown 对人和智能体友好。
YAML Front Matter 对程序友好。
标记区块支持安全局部更新。
JSONL 事件日志支持追加式历史记录。
后期即使接入数据库，Markdown 仍可作为可读视图和 Git 归档物。
```

推荐结构：

```text
Markdown 正文：给人和智能体读
YAML Front Matter：给程序读
Marked Sections：给程序或智能体安全更新
JSONL Events：追加历史事件
```

---

## 7. 对现有原型的影响

不推倒现有原型。

| 原型模块 | 决策影响 |
|---|---|
| 首页协作全景 | 保持，作为任务单状态与团队运行态聚合视图 |
| 项目健康总表 | 保持，作为项目任务账本与进度账本视图 |
| 团队详情页 | 保持，强化“组长维护任务清单”的解释 |
| 待决策工作台 | 保持，作为 Human-in-the-loop 节点 |
| 员工 Runtime 绑定 | 保持，作为后期 Runtime 编排预留 |
| 岗位 / 技能页 | 保持，作为 AgentTemplate / SkillMapping 表达 |

## 9. 后续观察点

满足以下条件时，再从阶段 A/B 升级到阶段 C/D：

```text
任务数量明显增加。
多个子智能体并发执行。
主智能体开始遗漏任务状态。
任务状态经常不一致。
用户需要更清晰的审计和恢复能力。
需要失败重试、超时处理和 Runtime 调度。
```

---

## 10. 决策摘要

```text
智能软件工厂当前不做完整复杂状态机。
第一阶段采用主智能体任务清单驱动。
任务单和任务事件是事实来源。
主子智能体通讯必须结构化回写。
Markdown 继续使用，但升级为带结构的 Markdown。
后续按轻量状态约束、程序状态机、Runtime 工厂化调度逐步演进。
```

## 11. task / taskflow 技能实践补充

在 v0.6.33 后续工作中，项目形成了两层技能实践：

```text
task：单任务质量闭环。
taskflow：外层任务流编排，按任务清单调用 task。
```

这套实践进一步验证了本 ADR 的核心决策：智能软件工厂不应依赖 Agent 自由聊天作为主流程，而应以任务清单、状态、门禁、评审和产物为核心。

### 11.1 对分阶段架构的补充证明

`taskflow → task(managed)` 的模式对应阶段 A/B：

```text
任务流清单 = 主智能体维护的任务账本
managed task = 被任务流编排的子任务
暂停门禁 = 待决策 / 阻塞 / 质量门禁
评审追踪 = 审查记录 / 质量证据
前后截图 = QA Artifact
```

这说明第一阶段可以先由主智能体或协作流程维护任务流，不必立即建设完整状态机。

### 11.2 对产品设计的边界约束

该技能实践是设计参考，而不是普通用户必须理解的功能。产品 UI 应继续展示用户可理解的项目推进、岗位产出、任务状态、审查、待决策和下一步动作；`taskflow`、`managed`、状态机、TaskEvent 等术语应主要出现在设计文档、开发任务和内部执行日志中。

### 11.3 对后续实现的建议

后续如果产品化，可优先实现：

```text
1. 结构化 Markdown 任务流清单。
2. 单任务质量闭环状态记录。
3. 暂停门禁与待决策映射。
4. 评审追踪表和 QA Artifact 持久化。
5. 任务流进度视图。
6. taskflow 调用 task 的 managed 执行语义。
```

该补充不改变本 ADR 的最终决策，只是将技能实践作为可落地参考写入架构依据。

## 12. 补充决策：暂停/恢复机制与串行/并行边界

本轮基于 `taskflow v0.3` 的技能实践，补充以下架构判断：

1. **暂停机制与待决策同构**：长程任务遇到关键决策、资料缺失、质量门禁或范围变化时，应暂停并等待用户补充，而不是直接失败。
2. **暂停必须可恢复**：用户补充信息后，应从暂停节点继续；已完成节点和产物不应重复执行。
3. **退出必须明确**：当质量不收敛、基线被破坏、工具不可用或计划方向错误时，应中断任务流，并明确已完成、未完成、风险和下一步建议。
4. **技能流是串行参考**：`taskflow` 默认一次推进一个节点，适合单智能体长程执行。
5. **智能工厂是并行协同系统**：正式产品化时，需要在 `taskflow` 串行参考之上增加并行任务调度、资源分配、冲突解决、跨团队依赖和多 Runtime 状态同步。

因此，`taskflow` 是智能工厂流程机制的低成本试验场，适合沉淀任务流、暂停/恢复、评审追踪和质量门禁格式；但不能把它等同为智能工厂最终的多智能体编排架构。


## 13. 补充决策：task v0.5.1 / taskflow v0.4.1 的边界经验

本轮技能试跑后确认：单任务执行与任务流编排必须严格分层。

决策如下：

1. `task` 代表单任务质量闭环，不能展示任务流节点图；
2. `taskflow` 代表多工作包编排，才展示任务流进度；
3. 当 SOW 不明确时，先由用户选择工作包，再生成任务流；
4. 任务流节点必须是可交付、可评审、可验收的工作包；
5. 暂停是可恢复状态，退出是不可继续或不建议继续；
6. 实际耗时必须来自记录，无法精确计时时必须明确标注。

该经验不会直接变成普通用户界面功能，但会作为后续智能工厂任务清单、待决策和多智能体编排设计的参考。


## 追加决策：taskflow v0.6 与智能工厂多智能体协同的边界

taskflow v0.6 的实践价值在于：以单智能体串行方式验证任务清单、SOW 选择、工作包级节点、质量门禁、暂停/恢复/退出和评审追踪等机制。

但智能工厂不是 taskflow 的直接复制。智能工厂面向多智能体协同，需要额外处理：

- 多个数字员工并行执行；
- RuntimeHost / RuntimeNode 的资源分配；
- 多工作区冲突与合并；
- 审查队列和返工队列；
- 任务单状态、事件和决策记录的持久化；
- 用户待决策工作台与恢复执行。

因此，taskflow 可作为轻量参考模型和技能实践，但正式系统仍应采用“主智能体任务清单驱动 → 轻量状态约束 → 程序状态机编排 → Runtime 工厂化编排”的分阶段演进路线。
